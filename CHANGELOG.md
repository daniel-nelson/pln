## 1.63.0 — 2026-09-04

### Changed

- **The Codex plan review now says the peer overlap works, because a run finally proved it.** `src/hosts/codex/plan-review-invoke.md` had been deliberately silent on this since 1.25.0, under the rule that a host fragment asserts only what has been verified — and no run existed, because on macOS the peer CLI's credential lives in the login keychain and Codex's sandbox denies it. With `sandbox_workspace_write.network_access = true` the peer resolves, and a real run then answered the question outright: three same-model readers spawned at 31.49m, 31.58m and 31.65m, the peer's shell call went out at 31.78m as a background cell before any await, the peer returned at 41.75m, and the readers were awaited after it at 42.36m. The round cost the slower of the two rather than their sum, which is the whole reason the slot runs beside them. The fragment records the run.

### Fixed

- **A cross-model peer's findings survive an enclosing code fence.** The reviewer brief already ends "No preamble, no code fence, no summary, no commentary", and a same-model reader obeys it. A peer is another vendor's model reading that instruction as best it can, and cannot be made to comply. On the first run where a peer was actually reachable, its adversarial review came back complete, on time and schema-shaped — wrapped in ```` ```json ````. The merge worker rejected the artifact as unparseable, the reader slot counted as failed, and the round lost model-family independence to three backticks while a same-model substitute re-did work the peer had already done. The merge contract now treats a single enclosing fence as transport rather than content: strip one leading fence and its matching trailer before parsing, say so, and reject what is still unparseable. Nothing else about validation softens — missing, empty, malformed, wrong-tree and uncited inputs remain failed readers after stripping.

## 1.62.0 — 2026-09-03

### Fixed

- **The final gauntlet settles what its commands need before the exact-once run, and an environment refusal is no longer a verification result.** The run is fingerprinted and happens once, so a command that cannot execute in the environment it is given does not fail verification — it destroys the attempt, and the whole gauntlet has to be re-fingerprinted and repeated. One run spent four attempts learning its own requirements from inside the run: a worker has no terminal, so a dependency preflight that wanted to clear a directory interactively aborted and took the API tests, evals, build and lint with it; a version-check script needed network and writable git metadata it was not granted at its first invocation; and a managed browser was refused the host access it needed to start. The contract now says to establish those requirements first — the unattended form of each command as the project documents it, network and filesystem access at the first invocation rather than the second, whatever a managed binary needs to launch — and to stop before the run when a requirement is not discoverable rather than learning it from a burned attempt. A missing terminal, a denied access, or a binary the host would not start is recorded as an environment failure naming the exact command and refusal: none of them is a claim about whether the tree satisfies the plan, and none may stand as a pass either. No toolchain is named anywhere in this: a project states the unattended form of its own commands, and the test pins that pln has not learned one package manager or one browser.

- **A plan directory outside the repository now gets an artifact directory workers can actually write.** 1.50.0 made a project-declared plan location outrank both defaults, which is right — a project that keeps plans outside the repository does so deliberately. But a native subagent inherits the coordinator's own write boundary, the repository and temporary space, and neither host lets the coordinator extend it for a child. So on a project whose instructions put plans in `~/Documents/`, native reviewers could read the plan and could not write their findings beside it, and the run improvised a temporary location per worker. When the plan directory sits outside the repository the coordinator now also allocates `pln-artifacts-<date>-<slug>` in temporary space, records it beside the plan path, and gives workers that path for evidence and results; it reads each validated envelope from there and writes the durable record into the plan directory, which only it can reach. Nothing durable lives there — the plan directory remains the record. Where the plan directory is inside the repository nothing changes and no second directory exists. `pln-read-envelope`'s `--root` follows the artifact directory rather than the plan directory, since the root confines the result to where the worker could actually write.

- **`pln-codex-agent` refuses an `--out` the brief also names.** `--out` captures the agent's final chat message, which is only ever a `RESULT_FILE=` pointer; the worker writes its bounded envelope to the path its brief assigns. A brief naming one path for both meant the wrapper truncated the envelope on start and overwrote it on finish, so the envelope reader got the pointer to itself and a completed evidence worker had to be re-run. The helper now checks the brief for the `--out` path and refuses with the reason and the way out. A distinct capture path is unaffected.

- **An optional review field is omitted, never abbreviated.** `structural_evidence` and `behavior_preservation` are optional and additive, but not loose: a partial object fails schema validation and takes its whole artifact with it. Three of four R3 readers returned cited findings, approximated `structural_evidence`, and lost their reader slots to a field none of them needed — nominal coverage of four, real coverage of one. The reviewer schema now says to omit either object entirely rather than emit a partial one: a reader that cannot fill every required field has a finding to report without it, not a shape to guess at.

## 1.61.0 — 2026-09-03

### Fixed

- **A question about the run's own bookkeeping never reaches the user.** The ask/decide/defer filter routes on authority and reversibility, and the fork test then asks whether the consequence is *material* — but never whether the user is better placed to answer than the agent. So a real `/pln` run put its own verification scaffolding to the user as an a)/b)/c) question: whether a shell check carried forward from a previous run should be annotated, edited in place, or dropped. It looked material — carried literally, one of those checks read as a permanent ban on ever editing a file — and the reply was "I don't understand any of this. Explain it simply." Two of the filter's own rules should have caught it. Its ask lane requires the deciding reason to live "in the user's head: domain fact, taste, risk appetite, business context", and none of those bear on a carried shell check. And its strongest tell, *you have a preference*, was firing: the turn spent a paragraph explaining which check was "the one worth your attention" and why it was a run-scoped promise misfiled as an invariant. The fork test now says what *theirs* excludes — this run's own apparatus, its scaffolding, records, and how state carries between runs — on the ground that its evidence is entirely in front of the agent. Incomprehension joins "sure" and "your call" as a miscalibration tell, as the worst of them. Room for the rule came out of the same section: a sentence that justified having one test rather than stating a rule.

## 1.60.0 — 2026-09-03

### Changed

- **Implementation runs one item at a time, in the working tree the run was launched in.** Concurrency arrived in 1.32.0 alongside the scheduler, cohorts and the manifest, and it was bought with a `git worktree add --detach` per isolated node — a bare checkout with no installed dependencies, no environment file, no database and no port block. Every worker then rebuilt that for itself, and none of it is anything git tracks, so no write lease could describe it and no dirty snapshot could protect it. Measured on one four-item run: thirty Postgres databases and 3.2 GB of worktrees left on the user's machine, three workers each independently copying the real `.env.test` and creating their own database, an entire scheduled item whose only product was repairing dependency state another worker had broken — its own result reads "Changed application files: none" — and then the three items executed serially anyway, because the runner the coordinator had chosen shares one authentication state. It paid every cost of isolation and collected none of it. `pln-scheduler build` now emits one node per wave and `ready` names one item, so linearity is structural rather than advisory; `claim` still answers about any node it is asked about. Dependencies still order the graph, cycles are still fatal, and leases keep their whole job and gain weight — they bound what a worker may write in the user's own tree and are validated against its diff at every checkpoint.

- **No worker builds an environment, and whoever moves the tree re-syncs it.** Removing isolation removes the *reason* workers provisioned, not the permission: nothing forbade it, and in the same run one item ran `pnpm install` three times while changing no tracked file. The item contract now draws the line where it belongs — adding or upgrading a package the item needs edits `package.json` and the lockfile, which are tracked files inside the lease and part of the diff, and the install that realizes it is that work; an install that changes no tracked file is rebuilding an environment, and is a blocker rather than a repair. If the project's own instructions say how a working environment is produced, the coordinator follows them once before any dispatch, because those instructions bind it; absent that, the environment is the directory the run was launched in. A lockfile change that an integration introduces is re-synced by the coordinator that integrated it, attributed to no item. An item whose only product is reconstructed environment state fails the node.

- **A cohort ends where the work stops being the same work, not at three nodes.** The cap had no justification anywhere in the repository and the coordinator called it "provisional", while sitting in a list whose other eight boundaries — subsystem, risk, skill, repository, malformed output, unexpected write, conflict, corrected premise — are all semantic. pln had already settled this shape once: assurance classifies risk semantically and lets numeric size *only escalate*. Cohorts now follow the same relationship. The boundaries decide, length follows from them, the schedule worker records why each cohort ends where it does, and context exhaustion joins the list because a worker carrying more evidence than its budget holds degrades as surely as one crossing a subsystem. A cohort beyond six nodes is a signal to re-derive the boundaries, stated as a backstop against a pathological plan and not as the criterion. Reuse is worth taking wherever the boundaries allow it: a fresh worker re-reads the plan, the root instructions and every mandated skill first, which on the observed run was about three thousand lines each.

- **`/pln-pr` may keep one worker across fix clusters it had to order.** Every independent cluster still starts fresh — a fix arriving at an untouched surface should not inherit another fix's reasoning about it. But clusters the scheduler ordered *because they collide* are not independent work that fresh context protects; they are one surface being changed twice, and a fresh worker there re-reads the review and every mandated skill to rediscover what the previous one just established. A Codex run named this cost itself: "the workflow requirement that every overlapping fix use a fresh worker, prove the regression first, run the focused suite, then checkpoint before the next worker starts". Independence is assurance when *finding* defects; a fix worker is doing work, and its diff is validated against its lease either way.

- **Native agents are the mechanism for item work, not one option among two.** Both hosts described their nested-CLI helper as what to do "on an older/disabled host without native collaboration" and neither said to check, or to prefer native. Observed: a coordinator used `spawn_agent` fourteen times without a failure, read the implementation phase, ran `pln-codex-agent --help`, and put every item, verification and repair through nested subprocesses for the rest of the run — subprocesses that share one authentication state and therefore cannot overlap. Taking the fallback is now a decision to disclose with its reason, and a run that has already spawned native agents in an earlier phase has its answer.

- **A wait that returns nothing new produces no message.** The lifecycle rule already forbade manufactured heartbeats; one run sent seventy-seven of them at a median of 1.1 minutes apart across an hour and a half — each a full model turn over the whole session context to report that nothing had happened. A prohibition with nothing said about the case that triggers it is a prohibition that loses. A wait returning no completed result, no blocker and no state change now produces no output at all: wait again. "The worker is still attached and below its timeout" is named as the sentence to recognise and not send.

## 1.59.0 — 2026-09-03

### Changed

- **The follow-up store is the project to-do list now, in every word pln says and on disk with it.** "Queue" was overloaded and also wrong on the merits: nothing in the store records a rank, urgency is two-state with no levels, and what can be picked up next comes from a write-set collision rather than arrival order. So it is one word everywhere — `bin/pln-queue` → `bin/pln-todo`, `QUEUE.md` → `TO-DO.md`, `q/` → `items/`, `done/` → `archive/`, `QUEUE_ROOT` → `TODO_ROOT`, `## Queue items` → `## To-do items` — and pln stops printing the store's slug ids to the user as if they were names, after a wrap-up that reduced an entire open question to `cross-repo-coordinated-plan` and nothing else. `TO-DO.md` rather than `TODO.md` because `TODO.md` is a file pln must never write, and the declared-file leg would otherwise adopt one and overwrite it. An existing store migrates once, in place, on first touch, on every resolution leg including the explicit `init --root`. The migration is resumable rather than atomic: each rename stands alone under the root-derived lock, the index is rebuilt last, and a re-run finishes whatever a kill left behind, so an interrupt leaves work to complete instead of a list the helper will not adopt. Two complete stores in one root refuse and name both. A store on an unwritable root is still read in place under the old names — "a read of the list never fails" is a shipped guarantee — and only the writers refuse. The `<!-- pln-queue v1` marker and the `queue-root:` header field are deliberately unchanged, because `bin/pln-scheduler` and `bin/pln-simplify` match on them and renaming them would make every store already on disk read as stray edits; both guards now accept either name set permanently. The `pln-queue: <path>` declaration key people wrote into their own instruction files still resolves, and two keys naming different places fail closed rather than letting whichever file is scanned first win quietly. **This is one-way.** A pln older than 1.59.0 cannot read a migrated store, and where two repositories share one declared root the older install does not merely fail to read it: it finds no `QUEUE.md`, declines the non-empty directory, and falls through to its create-and-ask default, making a second, empty to-do list beside the real one, silently, at exit 0.

- **pln says why a review was as deep as it was, instead of printing its own tier letter.** At nine places a person reads, pln announced `R1`–`R3`: "The R3 plan review ran broad, concurrency/transactions, and AI/eval-safety readers". That is pln's own coinage, defined in one policy file and nowhere else, so to the reader it was a label with no content — and it recurred often enough that a user assumed the gap was in their own knowledge. Every one of those sites now names the concrete trigger instead: "reviewed at the deepest setting, because this plan changes how money moves". Everything that rode with the letter is unchanged in force — which reader roles ran, whether a cross-model peer or a same-model substitute filled the adversarial slot, and `pln-peer`'s `REASON=` relayed rather than the bare status. The three warnings about a skipped review have no readers to name, so the trigger carries them alone, and where the top tier is the fail-closed default for work pln cannot classify, the sentence says so rather than asserting a risk nobody found. The letters stay wherever they are not a message: the assurance policy, the helper, the worker contracts, `REVIEW.md`'s persisted tier, the sealed evals corpus, and the skill description the picker reads.

- **One shared style rule now covers every term pln coined for its own machinery.** Both defects above are the same failure, and neither existing rule fired on them: the warning against a name you coined sat under a heading scoped to "anything the user has to act on", and a review-depth line is a disclosure, while the clause aimed at self-assembled terms lives in the Claude-only voice file and is about metaphors. The rule is now in shared style and binds every message rather than only the ones the user must answer — a coined handle or an internal slug belongs in a message only where that same sentence says what it is in ordinary words. Checked against both real specimens: a clause saying "R3", and a wrap-up whose entire ask was a to-do-list id.

- **The master-plan approval gate prints one numbered list instead of two.** The gate emitted the dashboard status list and a second list of what had been settled without the user, both starting at 1, in different vocabulary for the same items — and neither the triage line nor "reopen anything by number" said which list it indexed. Settled entries now hang under their item's dashboard row as `1a`, `2b`. Findings that land on the plan as a whole have no row to hang under, so they form a trailing group in their own visible space, `P1`, `P2`. The triage line and the reopen option each name what they index, and a bare item number reopens that item rather than being rejected. This reconciles two rules rather than dropping either: the item number is still the gate's reply-by-number address, and reopening is still defined in terms of a settled entry — the suffix addresses the entry under the row. Item numbers still never move; the scheduler depends on it.

- **1084 bytes of measured-evidence prose come out of the `/pln` router to fit the new rules under its 60000-byte ceiling.** The two rules above had to land in a file the test suite caps, and they left it 813 bytes over; raising the number was declined on an earlier plan as needing a defended new value rather than a quiet edit. Both trimmed passages argued that a rule is real rather than stating it — the six-day session tally behind the recommendation ladder with its "twice, pushed to restate" anecdote, and the two sentences counting how many user-facing turns leaned on plan-internal bookkeeping. Every rule either passage supported is still stated, in the same section. The Claude `/pln` router goes 60813 → 59729 and the Codex one 58044 → 56960.

## 1.58.0 — 2026-09-03

### Fixed

- **`pln-peer` says which of the two kinds of "no peer" it found, and they call for opposite things from the user.** `STATUS=none` covered both a machine with no second CLI on it and a peer that is installed, logged in, and whose credential the calling process cannot read — six identical lines, one meaning "install something" and the other "your host is sandboxing it". The root cause of a real run's seven consecutive `STATUS=none` results turned out to be the second: `claude auth status` prints `"loggedIn": false` and exits 1 inside Codex's seatbelt sandbox and `true` outside it, because Claude Code keeps its credential in the macOS login keychain and the sandbox denies that item (`security find-generic-password` exits 44 there and succeeds outside). The result contract gains a `REASON=` line — `no-peer-cli-found`, or `<peer>-not-authenticated:<resolved-path>` — making it nine lines rather than eight, always present and `none` when a peer is usable. The status vocabulary and every exit code are unchanged, so nothing keying on them learns a new value. The R3 substitution announcement now relays the reason rather than the bare status, because "pln could not find a peer" is both wrong and unactionable when a peer is installed, logged in, and merely walled off.

- **The R3 adversarial slot is dispatched with the rest of the roster whether a peer or a substitute fills it.** 1.52.0 told Codex to dispatch an R3 *peer call* before entering the wait loop, and named only the peer call — so the same-model substitute, which is what fills the slot whenever no peer is available, inherited no ordering at all. That is not the rare case: it is every run on a host whose sandbox hides the peer, which the fix above shows is the normal state of a sandboxed Codex session on macOS. Observed in a live run: three same-model readers spawned at 5463s, 5467s and 5472s, awaited at 5474s, and the adversarial substitute spawned at 5725s — adding that reader's entire runtime to the round rather than overlapping it. The rule now covers the slot rather than its occupant: a peer's shell call goes out before the wait loop, a substitute's spawn goes out among the other spawns, and the slot is the fourth reader either way.

## 1.57.0 — 2026-09-03

### Fixed

- **A forced update check resolves the ref instead of trusting a mutable CDN path, so a release merged seconds ago is seen.** 1.55.0 diagnosed the five-minute `raw.githubusercontent.com` edge cache correctly and then tried to talk the edge out of it — a client `Cache-Control: no-cache` and a varied query string — which does not work: a forced check 21 seconds after a merge still returned the previous version, from an install already carrying that fix. The real problem is that `.../<owner>/<repo>/main/VERSION` is a *mutable* path, where the same URL means a different file after every merge and a cached copy is indistinguishable from a current one. A forced check now resolves the ref with `git ls-remote`, which reads GitHub's git endpoint rather than the CDN — this is why `git pull` is never behind — and then reads VERSION at the returned sha, an immutable path where a cached copy can only be the right one. Two round trips, on a check the user explicitly asked for. Every step degrades to the previous behavior rather than failing: no `git`, a remote that is not `raw.githubusercontent.com` (the `PLN_REMOTE_URL` test override, a mirror, a fork served elsewhere), a failed `ls-remote`, or a pinned path that returns nothing all fall back to the plain URL, and a pinned fetch returning nothing is treated as a resolution problem rather than a verdict. The passive preamble check keeps the plain URL always, where a five-minute-old answer costs nothing and a second round trip on every invocation would not be paid for.

## 1.56.0 — 2026-09-03

### Fixed

- **A plan wider than one research wave no longer holds every question until the last wave lands.** 1.54.0 made item research concurrent, but the held-output rule releases when *the work* quiesces, and a wave is work: a plan needing four waves would consume wave one's envelopes silently, dispatch wave two, and keep holding — restoring in full the delay the waves were added to remove, for exactly the plans that can least afford it. The walk now begins when the first wave lands, and the next wave is dispatched as the walk moves into it. A wave still running for items the walk has not reached does not hold back a question about an item already researched: the hold exists so a message the user must read is not buried by later output, and a wave in flight produces no output — its results are consumed silently as they land, which the rule already says. One item is never split from its own research: its envelope is in hand before its question is asked.

On a host that injects those it is moot; on one that does not, the coordinator cannot learn the mandates governing its own conduct without reading them, and a repository whose `AGENTS.md` says "read `CLAUDE.md` in full before doing any work here" is owed that reading. Observed: a Codex coordinator read a 1050-line `CLAUDE.md` in four chunks — correctly, against pln's own text, and then correctly loaded the framework skill that file requires. A rule the model must break to behave well is the wrong rule. The exception is now stated, and the line drawn where it belongs: reading *further* on the strength of what the instruction file said is still the worker's job, not the coordinator's.

### Changed

- **The interview says plainly that research is all-items-first.** "Before the first proposal for every active item, classify the needed read" could be read as *each item as the walk reaches it*, which is a wait in front of every question rather than one wait in front of all of them. The intended shape — every active item researched before the walk begins — is now stated as the rule, with the per-item classification following from it.

## 1.55.0 — 2026-09-03

### Fixed

- **An explicitly requested update actually asks now, instead of answering out of the last upgrade's marker.** `pln-update-check`'s `--force` flag documents itself as busting the cache and the snooze, and it does — but the just-upgraded marker is checked before the fetch and never consulted `FORCE_CHECK` at all. So a forced check found the marker, printed `JUST_UPGRADED <old> <local>`, wrote `UP_TO_DATE <local>` into the cache with its 60-minute TTL, and exited without contacting the remote. With `auto_upgrade` on, that is the common case rather than a corner: an automatic upgrade writes the marker, and the explicit `/pln-update` or `$pln-update` a minute later is a guaranteed no-op that reports success and then silences the next hour of passive checks too. Observed end to end on 2026-09-03 — an explicit Codex update reported 1.52.0 → 1.53.0 without fetching, 43 seconds after 1.54.0 had been published. A forced check now consumes the marker, reports it, and carries on to the remote, so the news and the verdict arrive together.

- **The just-upgraded marker names the install that wrote it, so one host cannot claim another's upgrade.** `~/.pln/just-upgraded-from` is a single file shared by every installed copy, and whichever host read it first consumed it. In the same session as above, Claude Code performed the real 1.53.0 → 1.54.0 upgrade and the next Codex invocation reported it as its own. `pln-update-apply` now records which installs it upgraded alongside the version, and the check reports a writer it did not recognize as `upgraded by <install>` rather than presenting it as this host's work. A marker written before the field existed carries no writer and is given none.

- **A forced version check is no longer answered by a five-minute-old CDN copy.** The remote version is fetched from `raw.githubusercontent.com`, which serves `cache-control: max-age=300` from a Fastly edge — so a release merged and then immediately asked for can legitimately come back as the previous one, which is not how the same repository behaves under `git pull`. A forced check now sends `Cache-Control: no-cache` and varies the URL with a `pln_nocache` parameter so it cannot match a cached key. This is best-effort against a shielded cache rather than a guarantee, and it is built only for an `http(s)` remote: the `PLN_REMOTE_URL` test override is a `file://` path with no edge cache and no query string. The passive preamble check keeps the plain URL, where a five-minute-old answer costs nothing.

### Changed

- **A thirteenth test script.** `tests/update-check.sh` covers `bin/pln-update-check` and the marker `bin/pln-update-apply` writes for it, against a scratch state directory and a `file://` remote, so it needs no network: the passive path is still answered by the marker alone, the forced path reports the marker and still reaches the remote, the cache a forced check leaves behind carries the fetched verdict rather than a false `UP_TO_DATE`, a marker with and without a writer both report correctly, and the cache-buster stays restricted to http(s). It also pins that `UPDIRS` is initialized before the loop that appends to it, because an unset variable there aborts `pln-update-apply` under `set -u` on bash 3.2.

## 1.54.0 — 2026-09-03

### Changed

- **Interview research for independent items runs concurrently instead of one worker at a time.** The plan-review phase has always said "independent slots may run concurrently"; the interview phase said nothing of the kind, so a coordinator did the safe thing and spawned one research worker, awaited it, and only then spawned the next. ## 1.52.0 — 2026-09-02

### Changed

### Changed

- **A follow-up queue, so that work which is found and not done has one record.** A PR body, a review ledger and a commit message are copies; the queue is where someone goes to find out what is still outstanding. It is two things on disk: an index at `<queue-root>/QUEUE.md` carrying one line per open item, and one detail file per item under `q/`, complete enough that an agent with no memory of the conversation that produced it can pick the item up from that file and the repository alone. The line carries how far along the item is (`[ ]`, `[-]`, `[x]`), whether it is urgent, whether it can be picked up (`ready`, `blocked`, `decide`, `dropped`), what it is in ordinary words, and where the rest of it lives. Those three vocabularies are orthogonal, and the index is derived from the detail files rather than maintained by hand — `list` rebuilds it whole, so a line that disagrees with its detail file is the line that is wrong. Items group one level deep from a field on the item itself, and flagged items render in one `## Urgent` section rather than twice. `touches` (repository-relative paths, a directory standing for its subtree) and `holds` (non-file resources — a staging deploy, a migration slot, a shared prompt) are the only inputs to whether a second agent can take an item now: an overlap is refused naming the item and the path or resource shared, and an item filed with no `touches` is never reported parallel-safe, because otherwise the cheapest capture would be the most permissive thing in the queue. Nothing is deleted — a record that reaches a terminal state moves to `done/<YYYY-MM>/` and is listed in that month's own index. `bin/pln-queue` owns all of it (`init`, `add`, `list`, `check`, `claim`, `mark`, `archive`, `stale`), including resolving where the queue lives on every invocation, so a standalone `/pln-pr` run, a `/pln` run resumed after a restart, and a plan that predates this release all reach the same queue. pln grows no fourth skill and no slash command for it. A queue write is also not user-owned dirt: `pln-scheduler`'s dirty snapshot and `pln-simplify`'s clean-tree marker gate skip the queue's own paths beneath a root that actually holds a queue, and nothing above them — a bare `QUEUE.md`, `q` or `done` at the repository top level is still counted, so a root-level queue cannot disable either guard for the whole repository.

- **Work reaches the queue through four doors, and `/pln`, `/pln-pr` and `/pln-simplify` all file into it.** The sweep at either close files every candidate that clears the follow-up bar; an explicit "file this for a dedicated session", in whatever words and at whatever point, is filed in the turn it is said without pausing the phase it arrived in or becoming an interview question; a worker's out-of-scope discovery is filed by the coordinator at that item's checkpoint, workers never writing the queue themselves for the same reason they write neither `PLAN.md` nor the run manifest; and a `/pln-simplify` map files the candidates the run is not taking. Every door ends in the same `pln-queue add`, which writes the detail file, rebuilds the index from it, and prints back the index line it wrote. Filing never asks. Outflow is where the guards are: a run declares what it is taking with `claim`, which checks the collision and records the holder under one lock, and that declared set is the whole set it may ever check off; `[x]` means every part landed and `archive --disposition completed` refuses a record that is not already `[x]`, so the marking and the evidence cannot come apart; and an item finished some other way is archived only on the user's confirmation, with their words as the record's evidence — `pln-queue stale` reports candidates and never writes, and a merged commit naming an item's id archives nothing.

- **`/pln-simplify` captures follow-up work, which it never did before.** A map that finds eight bounded candidates and takes two produced six pieces of real work that ended with the run. Each candidate the run does not take — struck by the user at the outline checkpoint, or left behind by a run that stops there — is filed with `--source` naming the map and `--status decide` where what it needs is a decision rather than a pair of hands. Retained candidates go in before the skeleton is shown, because a run the user does not continue past the mandatory outline checkpoint ends there and no later step runs at all. Filing is not adopting: a filed candidate never becomes an item in that plan, and a `nothing worth changing` assessment files nothing.

- **A twelfth test script.** `tests/queue.sh` covers `bin/pln-queue` against a scratch queue and an isolated `HOME`: the resolution legs in order and what is never adopted (a symlink, a submodule mountpoint, someone else's directory, the repository top level, a bare repository), `add` returning the exact index line it wrote, `list` rebuilding the index in the derived order and failing closed rather than rendering an empty follow-up list, a refusal that names what it collides on, an atomic `claim` whose `--steal` names the holder it displaces, `mark` setting every vocabulary after filing, and `archive` moving a record where no subcommand deletes one. `tests/generate.sh` pins which generated files carry the queue format and that all twelve callers reach the helper by a resolved path; `tests/scheduler.sh` pins the dirty-tree exemption above against both helpers.

### Fixed

- **The ship hand-off fires from durable state, not from position in the step sequence.** Under either PR-bearing `Ship` value, Step 8 said to hand off "immediately at the end of Step 7's wrap-up" — a position in a file, which a to-do question, a compaction, a session restart or a user interruption all leave behind while the PR is still not open. ### Changed

- **Where the queue lives is settled once, at Step 1, and the close no longer asks anything about where follow-ups go.** `pln-queue init` resolves the project's own `pln/`, then the shared git directory, then a path the project's instructions declare, and reports every candidate it passed over rather than falling through in silence. When the question is still owed it is asked there, in a message of its own, with three answers and what each costs: committed at the project root, where it travels with a clone and appears in diffs; in the shared git directory, where every worktree reaches it and nothing is ever committed but a fresh clone starts empty; or outside the repository, where it survives worktrees and clones but teammates never see it and pln cannot find it again until a `pln-queue: <path>` line is added to the project's instructions. Outside a git worktree only the third exists. This replaces the to-do flow's "nothing found, ask once" branch, which asked at the close instead and asked in free form. - **A destination a project's instructions name but pln cannot make a queue root is no longer written to.** The to-do flow appended follow-ups "without asking" to a location named in either instructions file, and admitted an issue tracker as such a location; it also offered to write to a `TODO.md` found only by convention. A repo with a recorded duration polls rarely at first and more often as the expected finish nears; a repo with no history yet falls back to a fixed, sane default. Every round that reaches green records how long that round's CI actually took, so the next run — this one or a future one — starts smarter.
- **A red required check triggers a fix-and-rewatch loop, not a one-shot report.** The failing check becomes a new `REVIEW.md` finding, one fix cluster is dispatched through the existing Step 4 machinery, its commit is pushed, and the watch loop re-enters for another round — unbounded on how many rounds run, logged each time (failing check, what the fix cluster changed, the commit hash) in a new `## CI watch log` section of `REVIEW.md` so a later round's fix agent isn't starting blind. It stops only when green, or when "truly stumped": three consecutive rounds failing the *same* check, or a fix cluster's own `BLOCKED:` return (it couldn't find a concrete fix) — at which point the PR is left in draft and the blocker is surfaced to the user in the same shape as Step 4's needs-a-decision path.
- **All of this is gated behind a new `pr_draft` config key, default on**, following the exact `notify_push`/`notify_desktop`/`auto_upgrade` pattern — no special-casing added to `pln-config`, which was already a generic store. `pln-config set pr_draft false` fully reverts Step 8 to today's behavior: open ready immediately, with CI-watching mentioned only as something to start if the user asks for it, never started unprompted.

## 1.19.0 — 2026-07-22

### Changed

- **On Codex, pln now spawns fresh-context agents with the host's native multi-agent tools (`spawn_agent` / `wait_agent` / `resume_agent` / `close_agent`) instead of shelling out to a nested `codex exec` per item.** This is now a stated principle in `CLAUDE.md` — lean into the host's native primitives, don't reimplement them — because the reimplementation rots: by Codex CLI 0.145 the native multi-agent feature (`multi_agent`) is stable and on by default, so a model told to "spawn an agent and wait" reached for the native tool on its own and the nested-`codex exec` path additionally tripped the host's command-approval reviewer (`guardian_approval`) with a high-risk egress prompt on every launch. - **The spawn substrate (`Spawning a fresh-context agent`) is rewritten around the one thing that made the old runs hang: `wait_agent` is a bounded long-poll, not a blocking call that returns the result.** It comes back with a summary of which agents have an update — or with nothing on a quiet interval — so the orchestrator waits in a loop and stops only at a final status. Treating the first empty or timed-out wait as "the agent returned nothing" is exactly what renders as an endless `No agents completed yet`. The rewrite also pins pln to the V1 `multi_agent` surface and forbids enabling multi-agent V2, whose wait handler has a known bug (openai/codex#24342) that drops completion metadata and reproduces that same spin even after a child has finished.

The orchestrator still commits every item itself — stated now as the checkpoint-keeping choice it is, rather than "`.git` is read-only to the agent," since a native child's git access is the host's call. Blockers resume the same agent by its handle (its thread id on the fallback); finished agents are closed to free the small per-session concurrency slot.
- **`/pln-pr`'s review and fix armies move to native subagents too**, since they read the same substrate. The review army stays serial for now — the old "concurrent `codex` processes race on the shared OAuth token" reason is gone (native subagents are in-session threads, not separate processes), but a parallel army waits on many children at once, a pattern left to prove on-host before pln leans on it.

- **The nested-`codex exec` helper (`bin/pln-codex-agent`) is kept as a documented fallback for installs where the native tools are switched off or absent, not deleted.** Every call site leads with the native spawn and falls back to the helper, so a machine without the multi-agent tools still runs — it just pays the approval prompt the native path avoids. The helper's own guards are unchanged.

## 1.18.0 — 2026-07-21

### Added

- **The plan itself is now reviewed before you're asked to adopt it — a new Step 3.5 between the interview and the approval gate.** Every item's detail section has been written by the same model that ran the interview, carrying that conversation's assumptions and unable to see them; nobody has read the plan cold. Step 3.5 is that reading. A reviewer that never saw the interview is told to be adversarial, to skip what the plan gets right, to check the plan's factual claims against the files it names, and — per item — to take the problem the plan says exists today and ask whether the plan as written would actually have caught it. "Nothing worth changing" is stated as a complete answer, because a review required to produce findings manufactures them. It runs on every plan: there is no small-plan shortcut, since the reviewer's cost is reading the plan and already scales with it, and two items that change how every future run behaves are regularly worth more scrutiny than nine items of one-line edits. It's numbered 3.5 rather than renumbering Steps 4–8, which would have invalidated every cross-reference in both skills and every plan on disk that names a step.
- **The reviewer gets the plan and nothing else** — not the transcript, not your turns, not the options that lost. Two read-only audits settled that: 73 plan files across 13 repos and 261 hand-classified interview answers across 12 sessions. The transcript carries the writing model's own rationalizations next to your words, and a reviewer reading those is primed by the reasoning it was brought in to audit; quoting the rejected options re-argues a question you already closed. What makes the plan enough on its own is the new recording rule below. The brief ships as prose plus a paste-ready template, and the plan is inlined whole rather than referenced by path, because a peer may be a plain prompt-in/text-out CLI with no way to open a file — the paths are named too, for one that can.
- **A finding either corrects the plan or arrives at the gate flagged, and three tests decide which.** Applied only when all three hold: it is a false factual claim or a contradiction between two parts of the plan (the two kinds where being right is checkable without knowing what you want); it quotes what it rests on **and the quote is real**, verified by opening the file at that line before anything is applied (a peer with no repository access can still produce a well-formed, confident, invented citation); and it does not land on a decision you made in the interview. That last one holds even for a well-evidenced factual correction to the reason behind a decision — correcting a fact underneath a decision doesn't settle it, it gives you something new to weigh, and whether that changes the answer is yours. It's the blocker protocol one phase earlier. The correction isn't lost: it reaches the gate flagged, with its quote, so reopening it costs one reply. An applied correction is bounded to the sentences it lands on — no new items, no widened scope, no rewritten acceptance criteria — and is recorded in the item's detail section, which is what keeps it from being silent if context compacts between the review and the gate.
- **Second opinions now come from a peer model on both hosts, through one picker both skills share (`bin/pln-peer`).** Three rungs, in order: a command you named in `peer_command` (your whole invocation, so it can be a tool pln has never heard of — the contract is a pipe, prompt on stdin, answer on stdout); else a known agent CLI on your `PATH` that isn't hosting the session and is signed in — under Claude it reaches for `codex`, under Codex for `claude`; else nobody, which is a supported answer rather than a broken install. The helper prints exactly five lines (`RUNG`, `PEER`, `STATUS`, `RESULT_FILE`, `LOG_FILE`) so reading it costs almost no context, and an empty answer is treated as a failed peer rather than a peer that found nothing. Probes ship only for CLIs whose invocation pln has actually reproduced, since a probe that finds a command and calls it wrong is worse than finding nothing; everything else goes through the first rung. That required reproducing the non-interactive `claude` call the way `codex exec` was reproduced in 1.15.0 — **`bin/pln-claude-agent`**, with one deliberate difference from its Codex sibling recorded in its header: it does not unset `ANTHROPIC_API_KEY`, because a key is a legitimate auth method there and unsetting it would break installs that have nothing else. And `--allowedTools` is not what makes a peer read-only — it only *adds* permission rules, so a run given it still ran `ls -la` and created a file; `--tools` is the lever that restricts, and it's what ships.
- **pln asks once, per machine, before anything is ever sent to another vendor's CLI — and never again.** Rungs 1 and 2 hand your material to a CLI from another company: it leaves your machine and the call can spend your quota there. `peer_consent` in `~/.pln/config.yaml` has three states, not two — granted, declined, and *nobody has been asked*, which is what an absent key means (the repo's other booleans default on when unset, which is exactly wrong for a consent key). With no answer recorded the helper sends nothing, exits 5, and names the peer it would have used, so the question can name it too; `--which` and `--dry-run` answer `consent` first for the same reason. Declined is not an error and not a degraded run — the work happens on a fresh same-model agent and says so. The gate is enforced inside the helper, which every peer call passes through, so no call site can forget it, and it covers `/pln-pr`'s cross-model pass as well: the diff that pass used to send without asking now waits for the same one-time yes. A machine with no second CLI is never asked at all — a question that changes nothing is worse than no question.
- **Three new test scripts, all offline: `tests/peer.sh`, `tests/config.sh`, `tests/claude-agent.sh`.** The gauntlet is five scripts now, none of which needs a network, an agent CLI, credentials, or the developer's own `~/.pln`. `tests/peer.sh` runs fake `claude`, `codex` and rung-1 CLIs in front of a scrubbed `/usr/bin:/bin` PATH, with four different bin directories so a rung can be denied by *absence* rather than by a flag — a `--host` flag alone is not enough to deny a peer when the real CLI is installed. It covers the ladder in order, the skip-the-host rule in both directions, unauthenticated peers falling through (including the two shapes that exit 0 and are still unusable), the whole consent matrix asserting *nothing was sent* rather than just an exit code, and every failure status mapping to the right fallback. `tests/generate.sh` gained text assertions that both hosts' builds carry Step 3.5, the switch, the brief, all three of the applied lane's conjunctive tests and the never-move-a-decision rule — mutation-checked, not assumed.

### Changed

- **A decision in `PLAN.md` is now recorded in your own words, and this applies to every plan whether or not the review runs.** Auditing 261 interview answers found 51.7% are not self-contained — a bare letter, a letter plus a qualifier, a short corrective — and of the 112 of those that decided something, 102 (91%) become fully interpretable from the winning option's own line: the bolded label plus its em-dash clause, one line, exactly as pln already wrote it. So that's what gets copied, paired with everything you typed past the selector, verbatim and unsmoothed. Not the label alone ("flag for review", read a week later, names nothing) and not the option list (the losers are proposals you rejected, and the document implementers treat as the spec is the wrong place to keep them). Two real failures drove this: an answer of `c, but you don't need to run uspec` was written up as the content of option (a) — the agent's own recommendation — and a bare `a, 5 minutes for now` was given a justifying clause the user never said, which contradicted what the agent itself had argued two turns earlier. So a bare selector is now recorded as a bare choice, in those words: "no reason given". An invented rationale is indistinguishable from a real one, and the next reader — the reviewer, or an implementer weighing whether a hard failure justifies departing from the plan — treats it as something you would defend. Decisions you made are also marked as yours, which is what makes "never move a user decision" checkable rather than a guess.

One reply reopens any of them: a decision returns to the interview from its recorded position, an applied correction is shown with what it replaced and reverted on request (one edit, because the record carries the before text), a flagged finding becomes an interview question. A finding that lands on the plan as a whole rather than one item gets a number too, in a final group of its own. The gate also says in one clause who read the plan — the peer by name, or a fresh agent of the same model and why (no second CLI, consent off, or you asked to keep this plan local) — because you weigh a flagged finding differently depending on whose eyes were on it, and a review that found nothing gets the same clause, since silence there reads as if the step never ran. There's still one self-triage line for the whole list rather than one per kind: the single number space exists so there's one thing to scan and one way to reply. **When no review ran, the gate is exactly what it was** — no rung clause, no empty findings list, and no note explaining what didn't happen.
- **`/pln-pr`'s cross-model pass moved onto the same picker, and Codex gained one.** It used to be a hand-rolled `codex exec` block in the Claude build only; the Codex build said outright that "there is no second one to consult from here… Do not invent one." That line was a guard against a model improvising an unverified `claude` command line, not a position that Codex shouldn't consult one — reproducing the `claude` invocation removes the reason it existed. Both hosts now read the same passage, and both reach for whichever agent isn't running the session. The pass still skips (rather than falling back to a same-model rerun) when no peer is available, because a different model is its whole point.
- **The plan review is switchable, in two independent ways.** `plan_review false` in `~/.pln/config.yaml` turns it off for every plan in every repository; anything else, including an absent key, means on, so no existing install changes behavior on upgrade. Off is a clean no-op and a silent one — no brief assembled, no peer selected, no consent question, and no line explaining what didn't happen, which would be noise on every plan of someone who already opted out. A spoken instruction wins over the key for one run, in both directions ("skip the review" where it's on, "review this one" where it's off), and never writes to config. Three parts can be switched off separately: the whole step, the peer alone ("keep it local" — the review still runs, on a fresh same-model agent), or applying anything ("flag everything" — every finding reaches the gate, nothing is written into the plan).
- **`pln-config get` returns the value as written, spaces and flags and all.** It used to take the first whitespace-delimited token, which was fine while every key held a single-word boolean and impossible once a key has to hold a whole command line. The write path already stored the entire value, so the read path was the inconsistent half. One side effect worth knowing: `key:value` with no space after the colon used to read back empty and now reads back `value`.

### Fixed

- **`bin/pln-codex-agent` could not spawn an agent at all on a stock macOS install without coreutils** — it exited 127 before the CLI was ever called. `CMD=(env -u OPENAI_API_KEY "${TIMEOUT_CMD[@]}" codex exec)` expands an *empty* array when neither `timeout(1)` nor `gtimeout(1)` is present, and bash 3.2 — still the `/bin/bash` macOS ships, and what `#!/usr/bin/env bash` resolves to there — treats that as an unbound variable under `set -u`. Present since 1.15.0, and invisible to anyone whose PATH includes Homebrew's `timeout`, which is why it took a test that scrubs PATH to find it. Fixed in that helper and in the new `bin/pln-claude-agent`, with a deterministic `--timeout 0` case in both test scripts to hold the fix on every platform.

## 1.15.0 — 2026-07-21

### Added

- **The whole suite runs on OpenAI Codex, not just Claude Code — `/pln`'s implementation loop, `/pln-pr`'s review army, the blocker protocol, notifications and the routing rule all have a working Codex path.** Codex has always loaded pln's skills (its loader reads both `~/.agents/skills` and `~/.codex/skills`); what was missing was any host-aware text, so every mechanism the skills described — the `Workflow` script, the `Agent` tool, `resumeFromRunId`, `PushNotification` — named something that host does not have, and `/pln-pr` carried a Step 0.5 guard that stopped the run outright. On Codex a fresh-context agent is now `codex exec` driven by the orchestrator's own shell (Codex has no harness-run script to offload the loop into, so the loop lives in the orchestrator — pln's own pre-1.12 shape), a blocked item resumes the *same* thread via `codex exec resume <thread-id>` with the thread id captured at spawn and written into the item's handoff file, and the review army leads with native `codex review --base <branch>` followed by the lenses a generalist reviewer skips. Two host differences are deliberate and forced by the platform: Codex protects `.git` read-only even under `workspace-write`, so the spawned agent never runs `git commit`, `git stash` or `git add` — the orchestrator does all of it after a complete item, which preserves the invariant that matters (no commit for a partial item) while moving who runs the command; and review lenses run sequentially rather than in parallel, because Codex's OAuth refresh has no file lock and concurrent processes race on `auth.json`.
- **`bin/pln-codex-agent` — one helper that owns every sharp edge of spawning a nested `codex exec`.** Each of them fails silently, which is why they are a script instead of seven bullets restated at every spawn site: a non-TTY invocation hangs forever unless stdin reaches EOF (the brief is fed on stdin, which also removes a page of markdown from the shell-quoting path), an empty result file can arrive with exit code 0, there is no built-in run timeout so the process *group* has to be killed, `OPENAI_API_KEY` silently overrides OAuth and returns a misleading `401`, and `--last` races. The helper prints four `KEY=VALUE` lines (`STATUS`, `THREAD_ID`, `RESULT_FILE`, `EVENTS_FILE`) and keeps the agent's reasoning trace in a file the orchestrator never reads — the point of spawning an agent being to keep that out of its context. macOS ships no `timeout(1)`, so it resolves `timeout`, then `gtimeout`, then runs unbounded with a warning rather than refusing.
- **Two new test scripts, both offline: `tests/generate.sh` and `tests/codex-agent.sh`.** The generator suite drives fixtures through every directive, the banner, `--list`, `--clean` and eight error paths, then generates the *real* sources for both hosts and asserts each build contains none of the other's mechanics — absence is the property the whole design rests on, so it is the thing asserted, and the assertions were mutation-checked rather than assumed. The Codex helper suite runs against a fake `codex` on `PATH`: no install, no network, no credentials.

### Changed

- **`SKILL.md` and `pln-pr/SKILL.md` are now build output. The tracked sources live in `src/`.** `setup` runs `bin/pln-generate`, which composes a host-neutral core (`src/SKILL.core.md`, `src/pln-pr/SKILL.core.md`) with per-host fragments and variables (`src/hosts/claude/`, `src/hosts/codex/`) into the skill file for whichever host the copy is installed under — derived from the install path, since each host already gets its own full clone. Neither inline host branches nor a companion adapter file: both of those ask the model to do something (ignore text addressed to the other host, or remember to read a second file), and a model that gets it wrong fails silently. Generation moves the decision into a shell script, so by the time anything reads the skill, text for the other host is simply absent. The templating is three directives — include, strip, and literal `{{KEY}}` substitution — deliberately not a template language. Upgrades regenerate automatically (`bin/pln-update-apply` already runs `./setup`, and now restores the placeholders before stashing so the stash list can't grow on every upgrade), and `setup` warns when one clone is serving both host roots. **Editing `SKILL.md` directly no longer does anything** — a clone that has not run `./setup` carries a placeholder that says so. Installing via `npx skills` needs one manual `./setup` on first run, since that route executes no post-install step; it self-heals on the first `/pln-update`.
- **The routing rule installs itself where the host will actually read it, in wording that host can act on.** `bin/pln-routing-rule` derives its host from its own install root the same way `setup` does, and writes to `$HOME/.claude/CLAUDE.md` on Claude Code or `${CODEX_HOME:-$HOME/.codex}/AGENTS.md` on Codex — the latter verified empirically, not from docs, by finding a marker line in `codex debug prompt-input`. The Codex block is a separate, terser rule: it names the `pln-pr` skill rather than "invoke it via the Skill tool", a mechanism Codex does not have, and it is held under 700 bytes by the test suite because `AGENTS.md` is inlined in full on every single turn and silently truncated at 32 KB. Environment signals (`CODEX_HOME` set, `CLAUDECODE` set) are deliberately not used to pick the host — a user with both hosts installed has both signals in whichever session is running, and the question is which *copy* is being configured.
- **Notifications on Codex are desktop-only, and the skill says so instead of quietly doing nothing.** The phone-push channel is the harness `PushNotification` tool, which Codex has no ad-hoc equivalent for — its `notify` config hook is user-level and fires when a turn ends, on Codex's schedule rather than a skill's, so it cannot serve pln's three moments. `bin/pln-notify-desktop` already worked cross-host and becomes the whole story there; `notify_push` is documented as Claude Code only and no-ops. The Codex build still mentions the key in three lines, on purpose: a user who set it deserves an explanation rather than silence.
- **The docs describe what actually ships on each host.** README gains a Hosts section with a per-host mechanics table (who commits, parallel vs sequential reviewers, resume mechanism, notification channels), documents both Codex skill roots and both install paths, explains why `./setup` is not optional, and reorders the uninstall steps so the routing rule is removed *before* the pln directory is deleted — the helper is now the only thing that knows which global file to clean. `CLAUDE.md` gains the "the skill files are generated" rule and a rewritten Testing section naming all three test scripts.

## 1.14.0 — 2026-07-20

### Added

- **New `/pln-pr` skill: review a branch and open a pull request, the pln way.** It is the ship half of a plan — take the work on the current branch, review it, fix what the review finds, verify once, and open the PR — built to carry the review intelligence of a heavier ship tool without any of the runtime scaffolding. Trigger with `/pln-pr` or "put up a PR" / "open a PR" / "ship it", typically right after a `/pln` run but also standalone on any branch ahead of its base. A fresh-context review army runs as parallel subagents: six self-contained lenses (correctness, security, data/persistence, testing, maintainability/API-contract, performance) plus an adversarial generalist, with an optional Codex cross-model pass when `codex` is installed and authed. Every finding must quote the exact line that proves it or be forced below the confidence gate — the same false-positive-killing rule the review army depends on. Merged findings land in a durable `REVIEW.md` beside the plan before any fix runs, so an interrupted fix pass resumes from the file. Fixes run as fix subagents clustered by file (no two agents touch the same file), decisions surface one at a time as prose, and — the point of the whole design — the full gauntlet runs **once** at the end instead of after every fix cycle. A post-fix red-team subagent verifies the fixes hold and catches what the lenses missed. Self-contained: depends only on git, the harness Agent/Workflow tools, and optionally the GitHub/GitLab CLI and Codex. No external service, no server, no gstack — it never reads gstack checklists or assumes gstack is installed. VERSION/CHANGELOG bumping is conditional on the repo already using those files, so it imposes nothing on repos that don't.
- **`/pln-pr` triggering is reinforced so a compound instruction doesn't bypass the review.** Dogfooding surfaced the gap: "put up a PR" routed to the skill, but "bump the version and open the PR" was executed literally — bump, push, `gh pr create` — skipping the whole review army. Two layers close it. The skill's own triggers now explicitly claim PR asks embedded in a larger imperative ("and open the PR", "push this up"), while still honoring an explicit "skip the review". And a new opt-in global routing rule, installed via the consented preview-and-approve pattern (never automatically), tells the host to route every open/create/put-up-a-PR request through `/pln-pr`. The rule ships through a small idempotent helper, `bin/pln-routing-rule` (`--plan` previews, apply is a no-op if already present, writes to the user's global `~/.claude/CLAUDE.md` or `~/.agents/AGENTS.md`). `setup` offers it once at the end of a fresh install; `/pln-update` offers it once to existing users who upgrade without it; both gate on a `routing_prompted` marker so it never nags, and neither writes a single line without a yes.
- **`/pln-pr` was hardened after dogfooding it on its own PR (a `/pln-pr` self-review).** The routing helper now refuses to write without an explicit `--apply` and centralizes the offer text and gate behind a single `--offer` mode both call sites relay. The review flow was made fail-closed (an empty reviewer set stops rather than passing as "clean") and injection-safe (refs and PR bodies never interpolate into the shell). Note: existing users receive the routing offer on their *next* `/pln-update` after upgrading, not on the upgrade that installs 1.14.0 — a one-release delay that self-heals on the following run.

## 1.12.0 — 2026-07-08

### Changed

- **Step 5 now runs one Workflow script per implementation run instead of one Workflow invocation per item, in both interactive and auto mode.** Previously the orchestrator called Workflow once per item and waited for each item's notification before spawning the next; auto and interactive mode used the same mechanism but neither exploited Workflow's own resumability. Now the orchestrator builds a single script covering every pending item — the per-item loop lives inside the script, not in the orchestrator's own context — and invokes it once. On a blocker in interactive mode, the script returns immediately with the blocking question instead of trying to spawn a follow-up call itself (a running script has no channel back to the user mid-run); the orchestrator asks the user, records the answer, then resumes the same run via `resumeFromRunId` with the answer folded into `args`. Completed items replay from cache instantly since their `agent()` calls are unchanged; only the blocked item's call (now carrying the answer) and anything after it run live. Auto mode is unaffected in spirit — the script just doesn't stop on a blocker — but now shares the same one-script-per-run shape and gets the same resumability for free. Confirmed empirically: a script that deliberately returns early replays its completed prefix from cache on resume and continues past the return point, verified against the journal (no new `started` event for the already-completed step).
- **Auto-mode ⏸ blocked items now resolve at Step 6 through the same resume mechanism as an interactive blocker**, rather than being folded into the "revisit / push / drop" prompt used for deferred items. Each blocked item already has a concrete question recorded in its handoff file; Step 6 asks it directly and resumes the run.
- **The pending-item list for a run is now built fresh from `PLAN.md`'s status column, not carried as an in-memory cursor.** Guards against re-spawning an already-✅-done item if the orchestrator itself (not the Workflow run) gets re-invoked after an interruption.

### Fixed

- **`args` passed to a Workflow script arrives as a JSON string, not a parsed object.** Documented as a failure mode: any script logic that branches on an `args` field (as the new blocker-resume flow does) must `JSON.parse(args)` first, or the field reads as `undefined` silently. Discovered empirically while confirming the resumability behavior above.

### Fixed

- **The update check now scans every installed copy instead of stopping at the first one.** pln can be installed in more than one root at once (`~/.agents`, `~/.claude`, `~/.codex`, plus project-local variants), and the host often loads a different copy than the one that sorts first. ## 1.3.0 — 2026-06-24

### Changed

- **The implementation phase runs autonomously through per-item subagents.** Once the master plan is adopted, the main session becomes a thin orchestrator: it walks the items in order and spawns a fresh general-purpose subagent for each one, sequentially, with `PLAN.md` as the entire spec. The orchestrator never reads code or edits files itself, so its context stays light across the whole run and every item gets the blank-slate context a fresh session used to provide by hand. The subagent brief carries every per-item concern — mandated-skill invocation, lightweight verification, the commit, and memory capture — because the orchestrator is no longer doing that work. The orchestrator surfaces the question one-at-a-time, records the answer in `PLAN.md`, then spawns a fresh subagent that reads the handoff file and the uncommitted diff and resumes from where the first stopped — no work thrown away. A subagent commits only a complete, verified item, never partial work. Auto mode now means the orchestrator defers blockers (partial work stashed, item marked ⏸ blocked) to the end-of-run review instead of surfacing them immediately. - **Dream/Psychic learning capture is gated behind `RECORD_PSYCHIC_LEARNINGS`.** pln is general-purpose, so by default it no longer detects Dream/Psychic, writes a `WHAT_I_LEARNED_ABOUT_PSYCHIC_*.md` file, or mentions Dream/Psychic anywhere. ## 1.1.0 — 2026-06-10

### Changed

- **Interview asks only what only the user can answer.** Every open choice now routes through a filter with two checkable tests — *authority* (can you cite a concrete source that already decides this, by name?) and *reversibility of consequence* (can you name what would have to depend on it before it could change?). Unbacked-and-consequential choices become one-at-a-time interview questions; cite-backed or reversible choices are decided and disclosed; not-yet-knowable choices are deferred to implementation. This narrows the interview to the user-owned decisions and stops the indifferent-bare-letter answers that signalled a wasted question.
- **Disclosed-decisions list at the master-plan gate.** Decide-and-disclose calls are presented at Step 4 as a globally-numbered, item-grouped, **self-triaged** list — the few low-confidence calls flagged for review, the rest scannable. The user reopens any by number ("3, 7, 8") to drop back into the one-at-a-time interview, starting from the recorded position and its rationale; unlisted decisions stand as accepted.
- **One filter, two surfaces.** The same tests govern what the plan *prescribes*. `PLAN.md` records intent, constraints, acceptance criteria, and load-bearing/irreversible decisions at full fidelity, but no longer prescribes reversible implementation mechanics (sequencing, internal structure, exact commands) — those are left to the implementer. Decisions are recorded as overridable-when-reversible context, not imperative steps; guardrail boilerplate ("remember to test") becomes a stated qualitative bar. Plans read as goals, not step lists — better for capable implementers (Opus or Fable) without branching on the active model.
- **Plain conversational voice.** A new Style rule strips Claude's default "intense, over-confident tech bro" register from the skill's prose: minimal bold, no em-dash drama, no certainty-theater words ("load-bearing", "the crux", "exactly right"), claims stated once instead of as "not just X, it's Y", no agreement-amplifier openers, no restating the user's point back, no pre-labeling a point as significant ("it's a real fork") or announcing a question before asking it, no self-congratulatory adverbs ("cleanly", "elegantly"), no jargon or strained metaphors where a plain word works ("load-bearing", "moves the needle", "the rule that would bite"). Also leads with the answer instead of burying it under narrated reasoning, and matches response length to the question. Governs conversational prose only; the functional formatting (option labels, `[recommended]` marker, status icons, numbered sequences) is exempt. `/plnify` now installs a matching **Plain voice** section (its third) so gstack planning skills get the same register.
