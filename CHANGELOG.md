# Changelog

## 1.43.0 — 2026-08-27

### Added

- **A follow-up queue, so that work which is found and not done has one record.** A PR body, a review ledger and a commit message are copies; the queue is where someone goes to find out what is still outstanding. It is two things on disk: an index at `<queue-root>/QUEUE.md` carrying one line per open item, and one detail file per item under `q/`, complete enough that an agent with no memory of the conversation that produced it can pick the item up from that file and the repository alone. The line carries how far along the item is (`[ ]`, `[-]`, `[x]`), whether it is urgent, whether it can be picked up (`ready`, `blocked`, `decide`, `dropped`), what it is in ordinary words, and where the rest of it lives. Those three vocabularies are orthogonal, and the index is derived from the detail files rather than maintained by hand — `list` rebuilds it whole, so a line that disagrees with its detail file is the line that is wrong. Items group one level deep from a field on the item itself, and flagged items render in one `## Urgent` section rather than twice. `touches` (repository-relative paths, a directory standing for its subtree) and `holds` (non-file resources — a staging deploy, a migration slot, a shared prompt) are the only inputs to whether a second agent can take an item now: an overlap is refused naming the item and the path or resource shared, and an item filed with no `touches` is never reported parallel-safe, because otherwise the cheapest capture would be the most permissive thing in the queue. Nothing is deleted — a record that reaches a terminal state moves to `done/<YYYY-MM>/` and is listed in that month's own index. `bin/pln-queue` owns all of it (`init`, `add`, `list`, `check`, `claim`, `mark`, `archive`, `stale`), including resolving where the queue lives on every invocation, so a standalone `/pln-pr` run, a `/pln` run resumed after a restart, and a plan that predates this release all reach the same queue. pln grows no fourth skill and no slash command for it. A queue write is also not user-owned dirt: `pln-scheduler`'s dirty snapshot and `pln-simplify`'s clean-tree marker gate skip the queue's own paths beneath a root that actually holds a queue, and nothing above them — a bare `QUEUE.md`, `q` or `done` at the repository top level is still counted, so a root-level queue cannot disable either guard for the whole repository.

- **Work reaches the queue through four doors, and `/pln`, `/pln-pr` and `/pln-simplify` all file into it.** The sweep at either close files every candidate that clears the follow-up bar; an explicit "file this for a dedicated session", in whatever words and at whatever point, is filed in the turn it is said without pausing the phase it arrived in or becoming an interview question; a worker's out-of-scope discovery is filed by the coordinator at that item's checkpoint, workers never writing the queue themselves for the same reason they write neither `PLAN.md` nor the run manifest; and a `/pln-simplify` map files the candidates the run is not taking. Every door ends in the same `pln-queue add`, which writes the detail file, rebuilds the index from it, and prints back the index line it wrote. Filing never asks. Outflow is where the guards are: a run declares what it is taking with `claim`, which checks the collision and records the holder under one lock, and that declared set is the whole set it may ever check off; `[x]` means every part landed and `archive --disposition completed` refuses a record that is not already `[x]`, so the marking and the evidence cannot come apart; and an item finished some other way is archived only on the user's confirmation, with their words as the record's evidence — `pln-queue stale` reports candidates and never writes, and a merged commit naming an item's id archives nothing.

- **`/pln-simplify` captures follow-up work, which it never did before.** A map that finds eight bounded candidates and takes two produced six pieces of real work that ended with the run. Each candidate the run does not take — struck by the user at the outline checkpoint, or left behind by a run that stops there — is filed with `--source` naming the map and `--status decide` where what it needs is a decision rather than a pair of hands. Retained candidates go in before the skeleton is shown, because a run the user does not continue past the mandatory outline checkpoint ends there and no later step runs at all. Filing is not adopting: a filed candidate never becomes an item in that plan, and a `nothing worth changing` assessment files nothing.

- **A twelfth test script.** `tests/queue.sh` covers `bin/pln-queue` against a scratch queue and an isolated `HOME`: the resolution legs in order and what is never adopted (a symlink, a submodule mountpoint, someone else's directory, the repository top level, a bare repository), `add` returning the exact index line it wrote, `list` rebuilding the index in the derived order and failing closed rather than rendering an empty follow-up list, a refusal that names what it collides on, an atomic `claim` whose `--steal` names the holder it displaces, `mark` setting every vocabulary after filing, and `archive` moving a record where no subcommand deletes one. `tests/generate.sh` pins which generated files carry the queue format and that all twelve callers reach the helper by a resolved path; `tests/scheduler.sh` pins the dirty-tree exemption above against both helpers.

### Fixed

- **The ship hand-off fires from durable state, not from position in the step sequence.** Under either PR-bearing `Ship` value, Step 8 said to hand off "immediately at the end of Step 7's wrap-up" — a position in a file, which a to-do question, a compaction, a session restart or a user interruption all leave behind while the PR is still not open. The trigger is now a condition read out of durable state, the way `Ship` itself already was: false until Steps 6 and 7 are recorded done — every deferred item carrying the user's answer, the dashboard's Verification section carrying the gauntlet's per-command results and fingerprint hashes, and the sweep's outcome written to the plan — and true from there until `/pln-pr` has written `PR identity` in `REVIEW.md`, so the review, fix and blocker cycle the hand-off launched is not told on every turn to hand off again. While the condition holds the hand-off is the first action of the turn, and a hand-off that durable state records as decided but not yet performed now keeps the turn attached rather than letting it end.

- **The rule that "the Step 8 ship ask is a separate turn" implied there is always an ask.** Under either PR-bearing value there is none — the hand-off is an action, not a question — so a line meant to keep questions unbundled was putting a turn boundary in front of it in both hosts' to-do-location fragment. It now says which branches make an ask (`implement only`, an absent field, or a plan predating it) and what it is separate from.

- **A closing message's follow-up list is rendered from the queue rather than composed.** One said "Open follow-ups, all filed:" over six items when two were filed; the other four sat in a PR body and a review ledger for twelve hours, and every word of that message was written in good faith by a run that believed it. The order is now fixed — sweep, file, then draft — and the bullets are the lines `pln-queue list` reads back between its `INDEX_BEGIN` and `INDEX_END` markers, so a follow-up with no index line behind it has nothing to render it from, and the count describes a file rather than the run's account of its own behavior. A failed `list` is a failed read and fails the close with it. The one exception is a floor rather than a way out: when no queue root could be resolved or written at all, the run lists the follow-ups inline, says plainly that nothing was filed, and says why — losing them silently is the failure being fixed.

### Changed

- **Where the queue lives is settled once, at Step 1, and the close no longer asks anything about where follow-ups go.** `pln-queue init` resolves the project's own `pln/`, then the shared git directory, then a path the project's instructions declare, and reports every candidate it passed over rather than falling through in silence. When the question is still owed it is asked there, in a message of its own, with three answers and what each costs: committed at the project root, where it travels with a clone and appears in diffs; in the shared git directory, where every worktree reaches it and nothing is ever committed but a fresh clone starts empty; or outside the repository, where it survives worktrees and clones but teammates never see it and pln cannot find it again until a `pln-queue: <path>` line is added to the project's instructions. Outside a git worktree only the third exists. This replaces the to-do flow's "nothing found, ask once" branch, which asked at the close instead and asked in free form. An ignored in-project queue is no longer offered at all, because it is the combination worktrees break, and pln writes to no `.gitignore` or `.git/info/exclude` for the queue. Where the project's own instructions name a to-do *file*, the run offers once to migrate what is in it into the queue; the file is read and never written, appended to, or moved, and a declined offer is not re-asked.

- **A destination a project's instructions name but pln cannot make a queue root is no longer written to.** The to-do flow appended follow-ups "without asking" to a location named in either instructions file, and admitted an issue tracker as such a location; it also offered to write to a `TODO.md` found only by convention. A tracker cannot carry an index line, and a path named only in the global instructions file is per-machine — adopting it would give every repository on the machine one shared queue. Both now produce no queue root, so the follow-ups go to pln's own queue and the closing message names the destination it did not write to. Without that a user whose instructions name a tracker would assume the tracker has them.

## 1.42.0 — 2026-08-25

### Added

- **The adopt prompt leads with "implement it and open a draft PR when done".** Options b–e are the previous a–d, shifted down. The new option a differs from b in exactly one thing: the PR opens as a draft and stays one — `/pln-pr` still watches CI and still fixes what goes red, then closes with the PR in draft rather than marking it ready. On a team, ready is the signal that the branch is everyone else's to look at, and what any undrafting automation waits on, so this keeps that signal in the user's hands until they have read their own PR. It records `Ship: draft PR after implementation`, which Step 8 carries into `/pln-pr` as a `draft=keep` argument; `/pln-pr` records the disposition in `REVIEW.md` so a resumed run does not mark ready what it was told to leave alone. `draft=keep` can also be typed directly, and is the one argument that overrides the `pr_draft` config key — only in the safe direction.

## 1.41.0 — 2026-08-25

### Changed

- **The offer to walk the flagged entries is now option c of the adopt prompt.** It previously rode in prose beside the triage line, where it was easy to miss; the prompt is now four-way — implement and open a PR, implement only, walk the flagged entries, reopen by number — with the walk dropped (and the reopen option relettered c) when nothing was triaged. The walk itself is unchanged and still is not an adoption.

### Fixed

- **`pln-assurance fingerprint` and `pln-scheduler snapshot` no longer fail on a symlink to a directory.** `git hash-object` on the path follows the link and dies with `fatal: Unable to hash (null)`, so any repo with a tracked or dirty symlink pointing at a directory (a common shape for skill/plugin symlinks) could not produce a candidate fingerprint or dirty snapshot. Symlinks are now hashed the way git itself stores them — by their target string — which also means a retargeted link changes the fingerprint and a symlink is never mode-tested through its target.

### Changed

- **Findings and questions are held until the work in flight has quiesced, then presented one topic at a time with their own evidence.** A coordinator that spoke each time a worker, task, review, or peer call came back put substance the user had to read into a message that later output buried, then re-referred to it from a message further down — the second telling always thinner than the first. Every phase of `/pln`, `/pln-pr`, and `/pln-simplify` now consumes a completed result into the durable record silently while anything else is still outstanding. What it holds is a set of topics rather than a running log: one unit per question raised, carrying the evidence that question turns on, reconciled against later results before it is sent and after every answer. Each question then arrives with its own grounds attached, so no message depends on evidence the user had to catch in an earlier turn. A finding that raises no question earns no turn of its own and surfaces at the gate, the flagged-entry walk, or the closing sweep instead. A question already in front of the user is not overwritten by a landing result. One question at a time is unchanged; the host's activity surface and ignorable status lines stay exempt, and neither may carry a finding or a question.

## 1.38.0 — 2026-08-18

### Changed

- **Planning, implementation, and review now challenge unnecessary system surface throughout the lifecycle, and `/pln-simplify` provides recurring counter-pressure.** `/pln` compares proposed durable concepts with current owners before admitting a new one, implementation checkpoints account for reuse, consolidation, retirement, and justified compatibility, and the existing broad plan and PR reviews test structural fit without adding another permanent reviewer or cleanup quota. Every removal, replacement, or consolidation path shares one behavior-preservation contract: existing behavior-oriented specs are the primary admission gate and run on the recorded baseline before a simplifying plan or automatic repair is admitted. When coverage is missing, a new behavior spec must pass on the unchanged baseline and fail meaningfully when the protected behavior is deliberately broken. Implementation and PR repair then run the same admitted suite on the actual pre-change and post-change sources under equivalent conditions, while the full repository gauntlet remains the final regression floor; private reachability, absent references, or passing post-change tests alone cannot authorize simplification. That shared owner now emits one canonical `Safety disposition`: `retain` is the default, and only `admit` with every required conjunct marked `pass` and non-empty rerunnable evidence can enter a simplification item or automatic structural repair. The `/pln` coordinator and `/pln-pr` merge/fix seams validate and demote incomplete records, while consequential or destructive changes remain at their existing decision gates even when their behavioral proof is complete. The new host-neutral simplification workflow maps concepts and ownership, accepts `nothing worth changing`, reuses `/pln` for adopted work, verifies an unpublished exact candidate, records a portable content-bound commit marker, and exposes advisory cadence with an opt-in repository policy. `/pln-pr` checks that cadence, preserves one-run bypass boundaries, and propagates only a marker that still proves the resolved candidate.

## 1.36.0 — 2026-08-18

## 1.30.0 — 2026-08-12

### Changed

- **One test now decides what spends the user's attention, replacing two overlapping ones.** The interview routed choices by "authority or reversibility"; the plan review routed findings by "false claim, contradiction, quoted, not the user's." Both bars were low, both were worded differently, and between them a swap of one static landing page for another put **six agent decisions and ten review findings** in front of the user at the approval gate. One of the sixteen turned on anything they could have wanted either way; their replies to the rest were "yes, add it", "a", "fix it". **The fork test** is stated once and run by both surfaces: something reaches the user only when it **is a fork** — you can name two answers you would honestly implement, so one answer plus a defect is not one and neither is a completion the plan already forces — and when **the consequence is theirs and material**: visible behavior, scope, cost, risk, irreversible or external state, or work outside the approved item. One override outranks both: anything landing on a decision the user made goes to them regardless. Everything else is the work — make the least-scope repair that restores what the plan already says it wants, record it, move on.

- **Proportionality is now in the test rather than missing from it.** "Material" is what carries it: the same defect is a fork on a payments migration and quiet work on a static page, because being wrong does not cost the same. Review depth is unchanged — what scales is what interrupts.

- **A review finding is rejected, repaired, or flagged, and flagging is the smallest by a wide margin.** *Rejected* is new and is judged **by substance, never by phrasing**: reject only when the finding, taken as entirely true, changes nothing about whether the plan delivers its acceptance criteria. A finding that reads like internal plumbing and means "the job never fires" is a repair, not a rejection. **Every rejection is recorded** with its reason in the plan's review section — it is the one outcome where a finding disappears, so it is the one whose misfires are otherwise invisible. *Applied* is renamed *repaired* and gains omissions, which had no lane at all: a page needing three fonts where the plan vendors two used to reach the user however mechanical the fix.

- **The repair test is checkable by a stranger: name the outcome, quote the plan's own sentence stating it, name the change that restores it.** An earlier draft asked whether "exactly one completion is consistent" — uniqueness across an open solution space cannot be checked by a reader who never saw the interview, and a rule that demands it collapses into "the agent decides what's obvious", which is the failure it was meant to replace. Least-scope and recorded-outcome are checkable; unique is not.

- **A rule the user wrote is not a decision they made about this case.** Following their repo's convention repairs. But where applying it *here* is itself the question — whether this change is the kind the rule means — that is a fork and it is theirs. This user is on record overruling exactly such a call: "not a real break — listen, major version bump is reserved for real, intentional changes."

- **Findings that share a root are one entry.** A reduced-motion bug, an inline `:root` that beats the stylesheet, and two items contradicting about which wins are one question — *is it still shipping verbatim?* Numbering them apart asks the user to answer one question three times and to notice unaided that it was one. This is distinct from the existing merge of the *same* finding raised by both readers.

- **The gate's triage line got a real bar.** "Worth a look" now means your answer and theirs would produce different builds — harder than the fork test on purpose. Two or three entries is its usual size; a triage line naming half the list has triaged nothing.

### Fixed

- **The plan record was being used as a channel to the user.** Every quiet lane above ends "recorded in its item's section", and the skill never said what that record is for. It is for the implementer, the reviewer, and the next revision of this filter — **not** a way of telling the user, who does not open the file. Said out loud now, because it is the assumption the whole cut rests on: nothing that clears the fork test may be left to the record instead.

- **A disclosed call is said in the flow *and* numbered at the gate.** An intermediate draft collapsed the already-said ones into a count. That rested on a one-line disclosure having registered, and it lands mid-interview inside a message about something else — a line read past is not a decision ratified.

- **An internal contradiction introduced by the same draft**: one paragraph said a preference must never go unsaid, fifteen lines below a new rule making most of the lane unsaid. And a dangling cross-reference — the shared Style section named a section that exists only in `/pln`, so `/pln-pr` shipped a pointer to nothing.

## 1.29.0 — 2026-08-11

### Changed

- **A recommendation becomes a statement instead of a question.** The `[recommended]` option marker is removed and arguing for one option after the list is banned — but the call is now made *in the open, where it is made*, naming the option it beat and requiring no reply. Having a preference you can defend *is* the test the filter already applies for the decide-and-disclose lane, so a marked option means the routing was wrong; what it does not mean is that the preference should go unsaid. Measured over 170 recommendation-marked questions in six days of real sessions: 68 picked the marked option, **3 picked a different one, and 99 — 58% — did not answer with a letter at all**, correcting the framing or supplying a fact the options did not contain ("Where did that come from?", "is a misinterpretation of the changes"). So the ladder was almost never used as a ladder, and what earned its keep was the disclosure inside it: a recommendation the user can see is one they can catch being wrong, and they catch it by rejecting the premise, not by picking (b). The round trip goes; the visibility stays, and the decide-and-disclose lane now requires a rejected runner-up to be named in the flow, because the gate records a decision's rationale but never the option that lost.

- **The Step 4 gate no longer restates the plan or its own bookkeeping.** Three changes, from measuring a real 9,195-character gate: the per-item digest is gone, because every item's intent was settled with the user question by question in the interview they just finished; corrections the review applied are never listed, because a reviewer's finding you fixed in your own draft was never the user's to write or ratify (they were 16 of that gate's 36 numbered entries — 44% of the list, none of it actionable); and what remains is one numbered list of what the user has *not* seen, the disclosed decisions and the flagged findings. - **The poll interval adapts to a small per-repo CI-duration state value**, read and written through the same `pln-config` store every other setting already uses (`ci_duration_<owner-repo>` — operational telemetry, not the kind of durable fact the cross-session memory system is for). A repo with a recorded duration polls rarely at first and more often as the expected finish nears; a repo with no history yet falls back to a fixed, sane default. Every round that reaches green records how long that round's CI actually took, so the next run — this one or a future one — starts smarter.
- **A red required check triggers a fix-and-rewatch loop, not a one-shot report.** The failing check becomes a new `REVIEW.md` finding, one fix cluster is dispatched through the existing Step 4 machinery, its commit is pushed, and the watch loop re-enters for another round — unbounded on how many rounds run, logged each time (failing check, what the fix cluster changed, the commit hash) in a new `## CI watch log` section of `REVIEW.md` so a later round's fix agent isn't starting blind. It stops only when green, or when "truly stumped": three consecutive rounds failing the *same* check, or a fix cluster's own `BLOCKED:` return (it couldn't find a concrete fix) — at which point the PR is left in draft and the blocker is surfaced to the user in the same shape as Step 4's needs-a-decision path.
- **All of this is gated behind a new `pr_draft` config key, default on**, following the exact `notify_push`/`notify_desktop`/`auto_upgrade` pattern — no special-casing added to `pln-config`, which was already a generic store. `pln-config set pr_draft false` fully reverts Step 8 to today's behavior: open ready immediately, with CI-watching mentioned only as something to start if the user asks for it, never started unprompted.

### Changed

## 1.19.0 — 2026-07-22

### Changed

- **On Codex, pln now spawns fresh-context agents with the host's native multi-agent tools (`spawn_agent` / `wait_agent` / `resume_agent` / `close_agent`) instead of shelling out to a nested `codex exec` per item.** This is now a stated principle in `CLAUDE.md` — lean into the host's native primitives, don't reimplement them — because the reimplementation rots: by Codex CLI 0.145 the native multi-agent feature (`multi_agent`) is stable and on by default, so a model told to "spawn an agent and wait" reached for the native tool on its own and the nested-`codex exec` path additionally tripped the host's command-approval reviewer (`guardian_approval`) with a high-risk egress prompt on every launch. Native spawning runs under Codex's own approvals and sandbox, so neither happens.
- **The spawn substrate (`Spawning a fresh-context agent`) is rewritten around the one thing that made the old runs hang: `wait_agent` is a bounded long-poll, not a blocking call that returns the result.** It comes back with a summary of which agents have an update — or with nothing on a quiet interval — so the orchestrator waits in a loop and stops only at a final status. Treating the first empty or timed-out wait as "the agent returned nothing" is exactly what renders as an endless `No agents completed yet`. The rewrite also pins pln to the V1 `multi_agent` surface and forbids enabling multi-agent V2, whose wait handler has a known bug (openai/codex#24342) that drops completion metadata and reproduces that same spin even after a child has finished.
- **pln's per-item invariants are preserved on the native path, reframed off the mechanism they used to lean on.** The child gets a fresh context (`fork_turns: "none"`) but shares the orchestrator's working tree and sandbox, which is what Step 5's one-at-a-time, build-on-the-last-commit loop already wants. The orchestrator still commits every item itself — stated now as the checkpoint-keeping choice it is, rather than "`.git` is read-only to the agent," since a native child's git access is the host's call. Blockers resume the same agent by its handle (its thread id on the fallback); finished agents are closed to free the small per-session concurrency slot.
- **`/pln-pr`'s review and fix armies move to native subagents too**, since they read the same substrate. The review army stays serial for now — the old "concurrent `codex` processes race on the shared OAuth token" reason is gone (native subagents are in-session threads, not separate processes), but a parallel army waits on many children at once, a pattern left to prove on-host before pln leans on it.

### Fixed

- **The nested-`codex exec` helper (`bin/pln-codex-agent`) is kept as a documented fallback for installs where the native tools are switched off or absent, not deleted.** Every call site leads with the native spawn and falls back to the helper, so a machine without the multi-agent tools still runs — it just pays the approval prompt the native path avoids. The helper's own guards are unchanged.

## 1.18.0 — 2026-07-21

### Added

- **The plan itself is now reviewed before you're asked to adopt it — a new Step 3.5 between the interview and the approval gate.** Every item's detail section has been written by the same model that ran the interview, carrying that conversation's assumptions and unable to see them; nobody has read the plan cold. Step 3.5 is that reading. A reviewer that never saw the interview is told to be adversarial, to skip what the plan gets right, to check the plan's factual claims against the files it names, and — per item — to take the problem the plan says exists today and ask whether the plan as written would actually have caught it. "Nothing worth changing" is stated as a complete answer, because a review required to produce findings manufactures them. It runs on every plan: there is no small-plan shortcut, since the reviewer's cost is reading the plan and already scales with it, and two items that change how every future run behaves are regularly worth more scrutiny than nine items of one-line edits. It's numbered 3.5 rather than renumbering Steps 4–8, which would have invalidated every cross-reference in both skills and every plan on disk that names a step.
- **The reviewer gets the plan and nothing else** — not the transcript, not your turns, not the options that lost. Two read-only audits settled that: 73 plan files across 13 repos and 261 hand-classified interview answers across 12 sessions. The transcript carries the writing model's own rationalizations next to your words, and a reviewer reading those is primed by the reasoning it was brought in to audit; quoting the rejected options re-argues a question you already closed. What makes the plan enough on its own is the new recording rule below. The brief ships as prose plus a paste-ready template, and the plan is inlined whole rather than referenced by path, because a peer may be a plain prompt-in/text-out CLI with no way to open a file — the paths are named too, for one that can.
- **A finding either corrects the plan or arrives at the gate flagged, and three tests decide which.** Applied only when all three hold: it is a false factual claim or a contradiction between two parts of the plan (the two kinds where being right is checkable without knowing what you want); it quotes what it rests on **and the quote is real**, verified by opening the file at that line before anything is applied (a peer with no repository access can still produce a well-formed, confident, invented citation); and it does not land on a decision you made in the interview. That last one holds even for a well-evidenced factual correction to the reason behind a decision — correcting a fact underneath a decision doesn't settle it, it gives you something new to weigh, and whether that changes the answer is yours. It's the blocker protocol one phase earlier. The correction isn't lost: it reaches the gate flagged, with its quote, so reopening it costs one reply. An applied correction is bounded to the sentences it lands on — no new items, no widened scope, no rewritten acceptance criteria — and is recorded in the item's detail section, which is what keeps it from being silent if context compacts between the review and the gate.
- **Second opinions now come from a peer model on both hosts, through one picker both skills share (`bin/pln-peer`).** Three rungs, in order: a command you named in `peer_command` (your whole invocation, so it can be a tool pln has never heard of — the contract is a pipe, prompt on stdin, answer on stdout); else a known agent CLI on your `PATH` that isn't hosting the session and is signed in — under Claude it reaches for `codex`, under Codex for `claude`; else nobody, which is a supported answer rather than a broken install. The helper prints exactly five lines (`RUNG`, `PEER`, `STATUS`, `RESULT_FILE`, `LOG_FILE`) so reading it costs almost no context, and an empty answer is treated as a failed peer rather than a peer that found nothing. Probes ship only for CLIs whose invocation pln has actually reproduced, since a probe that finds a command and calls it wrong is worse than finding nothing; everything else goes through the first rung. That required reproducing the non-interactive `claude` call the way `codex exec` was reproduced in 1.15.0 — **`bin/pln-claude-agent`**, with one deliberate difference from its Codex sibling recorded in its header: it does not unset `ANTHROPIC_API_KEY`, because a key is a legitimate auth method there and unsetting it would break installs that have nothing else. And `--allowedTools` is not what makes a peer read-only — it only *adds* permission rules, so a run given it still ran `ls -la` and created a file; `--tools` is the lever that restricts, and it's what ships.
- **pln asks once, per machine, before anything is ever sent to another vendor's CLI — and never again.** Rungs 1 and 2 hand your material to a CLI from another company: it leaves your machine and the call can spend your quota there. `peer_consent` in `~/.pln/config.yaml` has three states, not two — granted, declined, and *nobody has been asked*, which is what an absent key means (the repo's other booleans default on when unset, which is exactly wrong for a consent key). With no answer recorded the helper sends nothing, exits 5, and names the peer it would have used, so the question can name it too; `--which` and `--dry-run` answer `consent` first for the same reason. Declined is not an error and not a degraded run — the work happens on a fresh same-model agent and says so. The gate is enforced inside the helper, which every peer call passes through, so no call site can forget it, and it covers `/pln-pr`'s cross-model pass as well: the diff that pass used to send without asking now waits for the same one-time yes. A machine with no second CLI is never asked at all — a question that changes nothing is worse than no question.
- **Three new test scripts, all offline: `tests/peer.sh`, `tests/config.sh`, `tests/claude-agent.sh`.** The gauntlet is five scripts now, none of which needs a network, an agent CLI, credentials, or the developer's own `~/.pln`. `tests/peer.sh` runs fake `claude`, `codex` and rung-1 CLIs in front of a scrubbed `/usr/bin:/bin` PATH, with four different bin directories so a rung can be denied by *absence* rather than by a flag — a `--host` flag alone is not enough to deny a peer when the real CLI is installed. It covers the ladder in order, the skip-the-host rule in both directions, unauthenticated peers falling through (including the two shapes that exit 0 and are still unusable), the whole consent matrix asserting *nothing was sent* rather than just an exit code, and every failure status mapping to the right fallback. `tests/generate.sh` gained text assertions that both hosts' builds carry Step 3.5, the switch, the brief, all three of the applied lane's conjunctive tests and the never-move-a-decision rule — mutation-checked, not assumed.

### Changed

- **A decision in `PLAN.md` is now recorded in your own words, and this applies to every plan whether or not the review runs.** Auditing 261 interview answers found 51.7% are not self-contained — a bare letter, a letter plus a qualifier, a short corrective — and of the 112 of those that decided something, 102 (91%) become fully interpretable from the winning option's own line: the bolded label plus its em-dash clause, one line, exactly as pln already wrote it. So that's what gets copied, paired with everything you typed past the selector, verbatim and unsmoothed. Not the label alone ("flag for review", read a week later, names nothing) and not the option list (the losers are proposals you rejected, and the document implementers treat as the spec is the wrong place to keep them). Two real failures drove this: an answer of `c, but you don't need to run uspec` was written up as the content of option (a) — the agent's own recommendation — and a bare `a, 5 minutes for now` was given a justifying clause the user never said, which contradicted what the agent itself had argued two turns earlier. So a bare selector is now recorded as a bare choice, in those words: "no reason given". An invented rationale is indistinguishable from a real one, and the next reader — the reviewer, or an implementer weighing whether a hard failure justifies departing from the plan — treats it as something you would defend. Decisions you made are also marked as yours, which is what makes "never move a user decision" checkable rather than a guess.
- **The Step 4 gate prints one numbered list of everything you can act on, not just the disclosed decisions.** Decisions made on your behalf, corrections the review applied, and findings it flagged now share a single number space, still grouped under their parent item, each entry opening with its kind because the three interleave. One reply reopens any of them: a decision returns to the interview from its recorded position, an applied correction is shown with what it replaced and reverted on request (one edit, because the record carries the before text), a flagged finding becomes an interview question. A finding that lands on the plan as a whole rather than one item gets a number too, in a final group of its own. The gate also says in one clause who read the plan — the peer by name, or a fresh agent of the same model and why (no second CLI, consent off, or you asked to keep this plan local) — because you weigh a flagged finding differently depending on whose eyes were on it, and a review that found nothing gets the same clause, since silence there reads as if the step never ran. There's still one self-triage line for the whole list rather than one per kind: the single number space exists so there's one thing to scan and one way to reply. **When no review ran, the gate is exactly what it was** — no rung clause, no empty findings list, and no note explaining what didn't happen.

That line was a guard against a model improvising an unverified `claude` command line, not a position that Codex shouldn't consult one — reproducing the `claude` invocation removes the reason it existed. Both hosts now read the same passage, and both reach for whichever agent isn't running the session. The pass still skips (rather than falling back to a same-model rerun) when no peer is available, because a different model is its whole point.
- **The plan review is switchable, in two independent ways.** `plan_review false` in `~/.pln/config.yaml` turns it off for every plan in every repository; anything else, including an absent key, means on, so no existing install changes behavior on upgrade. Off is a clean no-op and a silent one — no brief assembled, no peer selected, no consent question, and no line explaining what didn't happen, which would be noise on every plan of someone who already opted out. A spoken instruction wins over the key for one run, in both directions ("skip the review" where it's on, "review this one" where it's off), and never writes to config. Three parts can be switched off separately: the whole step, the peer alone ("keep it local" — the review still runs, on a fresh same-model agent), or applying anything ("flag everything" — every finding reaches the gate, nothing is written into the plan).
- **`pln-config get` returns the value as written, spaces and flags and all.** It used to take the first whitespace-delimited token, which was fine while every key held a single-word boolean and impossible once a key has to hold a whole command line. The write path already stored the entire value, so the read path was the inconsistent half. One side effect worth knowing: `key:value` with no space after the colon used to read back empty and now reads back `value`.

### Fixed

- **`bin/pln-codex-agent` could not spawn an agent at all on a stock macOS install without coreutils** — it exited 127 before the CLI was ever called. `CMD=(env -u OPENAI_API_KEY "${TIMEOUT_CMD[@]}" codex exec)` expands an *empty* array when neither `timeout(1)` nor `gtimeout(1)` is present, and bash 3.2 — still the `/bin/bash` macOS ships, and what `#!/usr/bin/env bash` resolves to there — treats that as an unbound variable under `set -u`. Present since 1.15.0, and invisible to anyone whose PATH includes Homebrew's `timeout`, which is why it took a test that scrubs PATH to find it.
