# Changelog

## 1.18.0 — 2026-07-21

### Added

- **The plan itself is now reviewed before you're asked to adopt it — a new Step 3.5 between the interview and the approval gate.** Every item's detail section has been written by the same model that ran the interview, carrying that conversation's assumptions and unable to see them; nobody has read the plan cold. Step 3.5 is that reading. A reviewer that never saw the interview is told to be adversarial, to skip what the plan gets right, to check the plan's factual claims against the files it names, and — per item — to take the problem the plan says exists today and ask whether the plan as written would actually have caught it. "Nothing worth changing" is stated as a complete answer, because a review required to produce findings manufactures them. It runs on every plan: there is no small-plan shortcut, since the reviewer's cost is reading the plan and already scales with it, and two items that change how every future run behaves are regularly worth more scrutiny than nine items of one-line edits. It's numbered 3.5 rather than renumbering Steps 4–8, which would have invalidated every cross-reference in both skills and every plan on disk that names a step.
- **The reviewer gets the plan and nothing else** — not the transcript, not your turns, not the options that lost. Two read-only audits settled that: 73 plan files across 13 repos and 261 hand-classified interview answers across 12 sessions. The transcript carries the writing model's own rationalizations next to your words, and a reviewer reading those is primed by the reasoning it was brought in to audit; quoting the rejected options re-argues a question you already closed. What makes the plan enough on its own is the new recording rule below. The brief ships as prose plus a paste-ready template, and the plan is inlined whole rather than referenced by path, because a peer may be a plain prompt-in/text-out CLI with no way to open a file — the paths are named too, for one that can.
- **A finding either corrects the plan or arrives at the gate flagged, and three tests decide which.** Applied only when all three hold: it is a false factual claim or a contradiction between two parts of the plan (the two kinds where being right is checkable without knowing what you want); it quotes what it rests on **and the quote is real**, verified by opening the file at that line before anything is applied (a peer with no repository access can still produce a well-formed, confident, invented citation); and it does not land on a decision you made in the interview. That last one holds even for a well-evidenced factual correction to the reason behind a decision — correcting a fact underneath a decision doesn't settle it, it gives you something new to weigh, and whether that changes the answer is yours. It's the blocker protocol one phase earlier. The correction isn't lost: it reaches the gate flagged, with its quote, so reopening it costs one reply. An applied correction is bounded to the sentences it lands on — no new items, no widened scope, no rewritten acceptance criteria — and is recorded in the item's detail section, which is what keeps it from being silent if context compacts between the review and the gate.
- **Second opinions now come from a peer model on both hosts, through one picker both skills share (`bin/pln-peer`).** Three rungs, in order: a command you named in `peer_command` (your whole invocation, so it can be a tool pln has never heard of — the contract is a pipe, prompt on stdin, answer on stdout); else a known agent CLI on your `PATH` that isn't hosting the session and is signed in — under Claude it reaches for `codex`, under Codex for `claude`; else nobody, which is a supported answer rather than a broken install. The helper prints exactly five lines (`RUNG`, `PEER`, `STATUS`, `RESULT_FILE`, `LOG_FILE`) so reading it costs almost no context, and an empty answer is treated as a failed peer rather than a peer that found nothing. Probes ship only for CLIs whose invocation pln has actually reproduced, since a probe that finds a command and calls it wrong is worse than finding nothing; everything else goes through the first rung. That required reproducing the non-interactive `claude` call the way `codex exec` was reproduced in 1.15.0 — **`bin/pln-claude-agent`**, with one deliberate difference from its Codex sibling recorded in its header: it does not unset `ANTHROPIC_API_KEY`, because a key is a legitimate auth method there and unsetting it would break installs that have nothing else. And `--allowedTools` is not what makes a peer read-only — it only *adds* permission rules, so a run given it still ran `ls -la` and created a file; `--tools` is the lever that restricts, and it's what ships.
- **pln asks once, per machine, before anything is ever sent to another vendor's CLI — and never again.** Rungs 1 and 2 hand your material to a CLI from another company: it leaves your machine and the call can spend your quota there. `peer_consent` in `~/.pln/config.yaml` has three states, not two — granted, declined, and *nobody has been asked*, which is what an absent key means (the repo's other booleans default on when unset, which is exactly wrong for a consent key). With no answer recorded the helper sends nothing, exits 5, and names the peer it would have used, so the question can name it too; `--which` and `--dry-run` answer `consent` first for the same reason. Declined is not an error and not a degraded run — the work happens on a fresh same-model agent and says so. The gate is enforced inside the helper, which every peer call passes through, so no call site can forget it, and it covers `/pln-pr`'s cross-model pass as well: the diff that pass used to send without asking now waits for the same one-time yes. A machine with no second CLI is never asked at all — a question that changes nothing is worse than no question.
- **Three new test scripts, all offline: `tests/peer.sh`, `tests/config.sh`, `tests/claude-agent.sh`.** The gauntlet is five scripts now, none of which needs a network, an agent CLI, credentials, or the developer's own `~/.pln`. `tests/peer.sh` runs fake `claude`, `codex` and rung-1 CLIs in front of a scrubbed `/usr/bin:/bin` PATH, with four different bin directories so a rung can be denied by *absence* rather than by a flag — a `--host` flag alone is not enough to deny a peer when the real CLI is installed. It covers the ladder in order, the skip-the-host rule in both directions, unauthenticated peers falling through (including the two shapes that exit 0 and are still unusable), the whole consent matrix asserting *nothing was sent* rather than just an exit code, and every failure status mapping to the right fallback. `tests/generate.sh` gained text assertions that both hosts' builds carry Step 3.5, the switch, the brief, all three of the applied lane's conjunctive tests and the never-move-a-decision rule — mutation-checked, not assumed.

### Changed

- **A decision in `PLAN.md` is now recorded in your own words, and this applies to every plan whether or not the review runs.** Auditing 261 interview answers found 51.7% are not self-contained — a bare letter, a letter plus a qualifier, a short corrective — and of the 112 of those that decided something, 102 (91%) become fully interpretable from the winning option's own line: the bolded label plus its em-dash clause, one line, exactly as pln already wrote it. So that's what gets copied, paired with everything you typed past the selector, verbatim and unsmoothed. Not the label alone ("flag for review", read a week later, names nothing) and not the option list (the losers are proposals you rejected, and the document implementers treat as the spec is the wrong place to keep them). Two real failures drove this: an answer of `c, but you don't need to run uspec` was written up as the content of option (a) — the agent's own recommendation — and a bare `a, 5 minutes for now` was given a justifying clause the user never said, which contradicted what the agent itself had argued two turns earlier. So a bare selector is now recorded as a bare choice, in those words: "no reason given". An invented rationale is indistinguishable from a real one, and the next reader — the reviewer, or an implementer weighing whether a hard failure justifies departing from the plan — treats it as something you would defend. Decisions you made are also marked as yours, which is what makes "never move a user decision" checkable rather than a guess.
- **The Step 4 gate prints one numbered list of everything you can act on, not just the disclosed decisions.** Decisions made on your behalf, corrections the review applied, and findings it flagged now share a single number space, still grouped under their parent item, each entry opening with its kind because the three interleave. One reply reopens any of them: a decision returns to the interview from its recorded position, an applied correction is shown with what it replaced and reverted on request (one edit, because the record carries the before text), a flagged finding becomes an interview question. A finding that lands on the plan as a whole rather than one item gets a number too, in a final group of its own. The gate also says in one clause who read the plan — the peer by name, or a fresh agent of the same model and why (no second CLI, consent off, or you asked to keep this plan local) — because you weigh a flagged finding differently depending on whose eyes were on it, and a review that found nothing gets the same clause, since silence there reads as if the step never ran. There's still one self-triage line for the whole list rather than one per kind: the single number space exists so there's one thing to scan and one way to reply. **When no review ran, the gate is exactly what it was** — no rung clause, no empty findings list, and no note explaining what didn't happen.
- **`/pln-pr`'s cross-model pass moved onto the same picker, and Codex gained one.** It used to be a hand-rolled `codex exec` block in the Claude build only; the Codex build said outright that "there is no second one to consult from here… Do not invent one." That line was a guard against a model improvising an unverified `claude` command line, not a position that Codex shouldn't consult one — reproducing the `claude` invocation removes the reason it existed. Both hosts now read the same passage, and both reach for whichever agent isn't running the session. The pass still skips (rather than falling back to a same-model rerun) when no peer is available, because a different model is its whole point.
- **The plan review is switchable, in two independent ways.** `plan_review false` in `~/.pln/config.yaml` turns it off for every plan in every repository; anything else, including an absent key, means on, so no existing install changes behavior on upgrade. Off is a clean no-op and a silent one — no brief assembled, no peer selected, no consent question, and no line explaining what didn't happen, which would be noise on every plan of someone who already opted out. A spoken instruction wins over the key for one run, in both directions ("skip the review" where it's on, "review this one" where it's off), and never writes to config. Three parts can be switched off separately: the whole step, the peer alone ("keep it local" — the review still runs, on a fresh same-model agent), or applying anything ("flag everything" — every finding reaches the gate, nothing is written into the plan).
- **`pln-config get` returns the value as written, spaces and flags and all.** It used to take the first whitespace-delimited token, which was fine while every key held a single-word boolean and impossible once a key has to hold a whole command line. The write path already stored the entire value, so the read path was the inconsistent half. One side effect worth knowing: `key:value` with no space after the colon used to read back empty and now reads back `value`.

### Fixed

- **`bin/pln-codex-agent` could not spawn an agent at all on a stock macOS install without coreutils** — it exited 127 before the CLI was ever called. `CMD=(env -u OPENAI_API_KEY "${TIMEOUT_CMD[@]}" codex exec)` expands an *empty* array when neither `timeout(1)` nor `gtimeout(1)` is present, and bash 3.2 — still the `/bin/bash` macOS ships, and what `#!/usr/bin/env bash` resolves to there — treats that as an unbound variable under `set -u`. Present since 1.15.0, and invisible to anyone whose PATH includes Homebrew's `timeout`, which is why it took a test that scrubs PATH to find it. Fixed in that helper and in the new `bin/pln-claude-agent`, with a deterministic `--timeout 0` case in both test scripts to hold the fix on every platform.

## 1.17.0 — 2026-07-21

### Removed

- **`/plnify` is gone.** Its only job was to copy pln's interaction rules into a user's global `~/.claude/CLAUDE.md`, so sessions that weren't running `/pln` would pick them up — the one thing pln did that a session without pln loaded could see. Writing to a user's global instructions is an antipattern for a shipped skill, and the sessions it was for are ones the user said they don't care about. pln now writes nothing outside its own directory, `~/.pln/config.yaml`, and the `plans/` folder in your own repo. Removing it does not undo a past run: if you ever ran `/plnify gstack`, open `~/.claude/CLAUDE.md` and delete the sections it appended — `## Interaction rules (override active skills)`, `## Exploratory mode (override active skills)`, and `## Plain voice (override active skills)`.
- **The opt-in PR-routing rule is gone**, along with the helper that installed it (`bin/pln-routing-rule`), the one-time offer in `setup` and in `/pln-update`, and `tests/routing-rule.sh`. Same reason: it was the other thing pln wrote into your global instructions. If you accepted the offer under 1.14.0–1.16.0, it left a marked block behind that stays until you remove it — delete the lines from `<!-- pln-pr-routing -->` through `<!-- /pln-pr-routing -->` inclusive, in `~/.claude/CLAUDE.md` on Claude Code or `$CODEX_HOME/AGENTS.md` on Codex. The `routing_prompted` marker in `~/.pln/config.yaml` is now vestigial and harmless.

### Changed

- **`/pln` hands off to `/pln-pr` at the end of its own workflow.** The routing the deleted global rule used to buy now lives where it works for the sessions you actually run. A new final step treats shipping as invoking `/pln-pr`, so a PR ask anywhere in the run — including one folded into a larger instruction like "bump the version and open the PR" — routes through the review army instead of a bare `git push` and `gh pr create`. It asks once, at the end of the run, before shipping; it is skipped when nothing is ahead of the base branch or when you already said where the run ends, and it still honors an explicit "skip the review". Claude Code invokes the skill through the Skill tool; Codex reads `pln-pr/SKILL.md` by name.
- **`/pln` and `/pln-pr` share one Style section.** Both skills now read the same style rules from a single source (`bin/pln-generate` gained a `src/shared/` fallback for `pln:include`), so a rule added once reaches both. This also retires a reference in `/pln-pr` to "the recommended-option format from the user's global config" — a pointer that dangled the moment the global file was empty and that removing `/plnify` would have broken for good.

### Added

- **Two Style rules for how a message ends, now shared by both skills.** Every message that isn't one of the three interview shapes closes with at most one line — `DECIDE:` (one question), `DO:` (one action), or `HEADS-UP:` (something you would regret not knowing) — or nothing at all. A brief work-completed line sits above it, says what was done and stops, and is skipped when nothing was done. On Claude Code a further rule holds or drops a fact that has no bearing on what you do next. All three come from sections the user had written for their own global instructions before pln existed; folding them into the skill is part of what let the global file go away.

## 1.16.0 — 2026-07-21

### Changed

- **Interview messages now follow one of three literal templates instead of a described order.** Step 3 used to say: open with a plain-language summary, then the evidence the options turn on, then the question. Three transcript samples across 376 interview messages and 68 sessions found a median 57%, 59% and 62% of an option message sitting above the first lettered option — the file doing exactly what it asked for, and the reason the user could not tell what a message wanted from him without reading all of it. That sentence is gone. A new `Message shape` subsection carries a slot spec and a worked example for each of the three kinds of message the skill actually sends: an option message, a binary question, and a reaction or finding. Each one leads with the line that says what the message is, so position carries the signal. Templates were chosen because they are the form this file already gets obeyed in: specs showing literal surface syntax are followed, specs describing content selection are not, and every measured failure was in the second group. Three rules follow the examples: the sentence naming the decision uses plain words, evidence that only establishes the problem is real gets cut (evidence that changes which answer wins stays, at any length — there is no word limit anywhere in this release), and a prior conclusion is named in a clause rather than re-argued, so the user never scrolls up to answer.
- **The voice rules are per-host now, and the Codex build no longer carries Claude's.** `Conversational voice` was written across one day in June against a specific complaint about Claude's register, one bullet per sentence the user caught. It is the only part of `/pln` whose justification is a model's behavior rather than a workflow's requirement, and it was being served to Codex, whose output across four long documents in one session showed almost none of them. The subsection is now a `pln:include voice` fragment: `src/hosts/claude/voice.md` carries it verbatim, and `src/hosts/codex/voice.md` starts nearly empty with four rules Codex named for itself — keep in-flight commentary operational, don't turn an interview turn into a report, don't widen the plan to adjacent work, and only carry repository evidence that changes the answer. Everything that is not a register correction stayed in core and reaches both hosts: the three message templates, the naming rule, the answer-shape rule, and the pre-send check. The Claude build is byte-identical across this split; the Codex build loses 592 words of guidance aimed at a register it does not have.
- **Option descriptions are parallel, the recommendation is stated once, and an echo line carries the answer and nothing else.** Measured against a spec that said "short description", option descriptions ran a 24–27 word median with a maximum of 125, and the recommended option ran 1.6× the length of the alternatives because it was carrying the argument for itself. The recommendation appeared twice in 31% of option messages and three times in 9%. `Discrete option choices` now says every description answers the same questions in the same order, parallel in shape and not in length. `Recommended option marker` says the recommended option gets no extra words for being recommended and nothing after the list restates which one you picked. Echo lines, measured at a 22.5-word median against a spec saying "one short line", now name the three things that inflate them: the reason, the effect, and the lead-in to the next question. No word caps were added; the rules name content, not length.
- **"Don't restate the user's point back" widened to cover anything already said in the conversation, yours or the user's, and absorbed the rule that contradicted it.** A separate bullet told the model to restate anything referenced by shorthand, which read as licence to re-explain. The two are one rule now: naming a prior conclusion is required and gets one clause in plain words, not a shorthand like "H1" or "the repro above" and not the argument that produced it.
- **A bare-letter reply is no longer read as a sign the question shouldn't have been asked.** The file told the model that answering with a single letter means the ask/decide filter is miscalibrated. It doesn't; it means an option was selected. Genuinely indifferent answers ("sure", "your call", "whatever's easiest") still carry that signal and still appear.
- **The failure-modes list went from 28 bullets to 7 on Claude and 32 to 11 on Codex.** It had grown into a second copy of the style rules — self-containment, the bare-letter tell, and the whole voice section each appeared in both places. Every bullet that only restated a rule stated elsewhere is gone, checked one at a time against the generated build rather than against `src/` so a `pln:only` variant was never miscounted. Bullets describing a failure nothing else covers all stayed. The reason to do this at all: the evidence is consistent with instruction-following degrading as instruction volume rises, and a file that says "state a claim once" three times is not credible. Net across the whole release, the Claude build grew 89 words and the Codex build shrank 500.
- **The Step 4 gate asks for a digest of each item, which is what it was already printing.** It said "Print each item's detail section, in order," and the measured gate ran a 422-word median — nowhere near that. It now asks for each item's title, what it does in a sentence or two, and any decision later items rest on, with the detail sections left in `PLAN.md` to open. Reprinting them buried the disclosed decisions, which are the part that needs a reaction.
- **Two voice rules added in 1.10.0 are gone.** "Say what each piece of evidence shows" mandated sentences whose content is the relation between two other sentences, and issued the em-dash construction the rule two lines above it forbids. "One argumentative move per paragraph" removes no words and adds a transition sentence to reconnect the halves. Both manufactured the prose this release is trying to cut.

### Added

- **Three new Style subsections, each aimed at a failure no existing rule reached.** `Naming things the user reads`: an item number, question number, line number or commit hash is an address into a file the user does not have open, so it never stands alone as the name for something — pair it with the thing or leave it out. The file's own echo examples read `"Q5 recorded: …"`, so it was teaching the behavior; they now read `"Recorded: …"`. `What each answer changes`: anything the user has to act on says what changes with each answer it offers, and a name you coined ten turns ago gets restated every time you ask about it — this one was caught live, when two items were flagged for decision using phrases defined much earlier and never restated. `Before you send`: take each sentence out of the draft and read what is left; if no fact went out with it, leave it out. That last one is the only test that reaches a sentence with the grammar of a claim and nothing in it, which is the shape the user named as what exhausts him.
- **A before/after rewrite by the user ships as the worked example for register.** "Would the user have written it this way?" has been in the file for months with no referent — the model has no model of the user's prose. It has one now: the model's sentence, the user's rewrite of it, and the three moves between them (give the sentence a subject and a verb, don't hide the verb in a noun, cut the evidence that only proves the problem exists). The jargon rule also gained one clause, because every phrase flagged in the message that started this was a first-generation coinage rather than anything on a blocklist: a multi-word noun phrase you assembled yourself to be precise counts as jargon too.

## 1.15.0 — 2026-07-21

### Added

- **The whole suite runs on OpenAI Codex, not just Claude Code — `/pln`'s implementation loop, `/pln-pr`'s review army, the blocker protocol, notifications and the routing rule all have a working Codex path.** Codex has always loaded pln's skills (its loader reads both `~/.agents/skills` and `~/.codex/skills`); what was missing was any host-aware text, so every mechanism the skills described — the `Workflow` script, the `Agent` tool, `resumeFromRunId`, `PushNotification` — named something that host does not have, and `/pln-pr` carried a Step 0.5 guard that stopped the run outright. On Codex a fresh-context agent is now `codex exec` driven by the orchestrator's own shell (Codex has no harness-run script to offload the loop into, so the loop lives in the orchestrator — pln's own pre-1.12 shape), a blocked item resumes the *same* thread via `codex exec resume <thread-id>` with the thread id captured at spawn and written into the item's handoff file, and the review army leads with native `codex review --base <branch>` followed by the lenses a generalist reviewer skips. Two host differences are deliberate and forced by the platform: Codex protects `.git` read-only even under `workspace-write`, so the spawned agent never runs `git commit`, `git stash` or `git add` — the orchestrator does all of it after a complete item, which preserves the invariant that matters (no commit for a partial item) while moving who runs the command; and review lenses run sequentially rather than in parallel, because Codex's OAuth refresh has no file lock and concurrent processes race on `auth.json`.
- **`bin/pln-codex-agent` — one helper that owns every sharp edge of spawning a nested `codex exec`.** Each of them fails silently, which is why they are a script instead of seven bullets restated at every spawn site: a non-TTY invocation hangs forever unless stdin reaches EOF (the brief is fed on stdin, which also removes a page of markdown from the shell-quoting path), an empty result file can arrive with exit code 0, there is no built-in run timeout so the process *group* has to be killed, `OPENAI_API_KEY` silently overrides OAuth and returns a misleading `401`, and `--last` races. The helper prints four `KEY=VALUE` lines (`STATUS`, `THREAD_ID`, `RESULT_FILE`, `EVENTS_FILE`) and keeps the agent's reasoning trace in a file the orchestrator never reads — the point of spawning an agent being to keep that out of its context. macOS ships no `timeout(1)`, so it resolves `timeout`, then `gtimeout`, then runs unbounded with a warning rather than refusing.
- **Two new test scripts, both offline: `tests/generate.sh` and `tests/codex-agent.sh`.** The generator suite drives fixtures through every directive, the banner, `--list`, `--clean` and eight error paths, then generates the *real* sources for both hosts and asserts each build contains none of the other's mechanics — absence is the property the whole design rests on, so it is the thing asserted, and the assertions were mutation-checked rather than assumed. The Codex helper suite runs against a fake `codex` on `PATH`: no install, no network, no credentials.

### Changed

- **`SKILL.md` and `pln-pr/SKILL.md` are now build output. The tracked sources live in `src/`.** `setup` runs `bin/pln-generate`, which composes a host-neutral core (`src/SKILL.core.md`, `src/pln-pr/SKILL.core.md`) with per-host fragments and variables (`src/hosts/claude/`, `src/hosts/codex/`) into the skill file for whichever host the copy is installed under — derived from the install path, since each host already gets its own full clone. Neither inline host branches nor a companion adapter file: both of those ask the model to do something (ignore text addressed to the other host, or remember to read a second file), and a model that gets it wrong fails silently. Generation moves the decision into a shell script, so by the time anything reads the skill, text for the other host is simply absent. The templating is three directives — include, strip, and literal `{{KEY}}` substitution — deliberately not a template language. Upgrades regenerate automatically (`bin/pln-update-apply` already runs `./setup`, and now restores the placeholders before stashing so the stash list can't grow on every upgrade), and `setup` warns when one clone is serving both host roots. **Editing `SKILL.md` directly no longer does anything** — a clone that has not run `./setup` carries a placeholder that says so. Installing via `npx skills` needs one manual `./setup` on first run, since that route executes no post-install step; it self-heals on the first `/pln-update`.
- **The routing rule installs itself where the host will actually read it, in wording that host can act on.** `bin/pln-routing-rule` derives its host from its own install root the same way `setup` does, and writes to `$HOME/.claude/CLAUDE.md` on Claude Code or `${CODEX_HOME:-$HOME/.codex}/AGENTS.md` on Codex — the latter verified empirically, not from docs, by finding a marker line in `codex debug prompt-input`. The Codex block is a separate, terser rule: it names the `pln-pr` skill rather than "invoke it via the Skill tool", a mechanism Codex does not have, and it is held under 700 bytes by the test suite because `AGENTS.md` is inlined in full on every single turn and silently truncated at 32 KB. Environment signals (`CODEX_HOME` set, `CLAUDECODE` set) are deliberately not used to pick the host — a user with both hosts installed has both signals in whichever session is running, and the question is which *copy* is being configured.
- **Notifications on Codex are desktop-only, and the skill says so instead of quietly doing nothing.** The phone-push channel is the harness `PushNotification` tool, which Codex has no ad-hoc equivalent for — its `notify` config hook is user-level and fires when a turn ends, on Codex's schedule rather than a skill's, so it cannot serve pln's three moments. `bin/pln-notify-desktop` already worked cross-host and becomes the whole story there; `notify_push` is documented as Claude Code only and no-ops. The Codex build still mentions the key in three lines, on purpose: a user who set it deserves an explanation rather than silence.
- **The docs describe what actually ships on each host.** README gains a Hosts section with a per-host mechanics table (who commits, parallel vs sequential reviewers, resume mechanism, notification channels), documents both Codex skill roots and both install paths, explains why `./setup` is not optional, and reorders the uninstall steps so the routing rule is removed *before* the pln directory is deleted — the helper is now the only thing that knows which global file to clean. `CLAUDE.md` gains the "the skill files are generated" rule and a rewritten Testing section naming all three test scripts.

## 1.14.0 — 2026-07-20

### Added

- **New `/pln-pr` skill: review a branch and open a pull request, the pln way.** It is the ship half of a plan — take the work on the current branch, review it, fix what the review finds, verify once, and open the PR — built to carry the review intelligence of a heavier ship tool without any of the runtime scaffolding. Trigger with `/pln-pr` or "put up a PR" / "open a PR" / "ship it", typically right after a `/pln` run but also standalone on any branch ahead of its base. A fresh-context review army runs as parallel subagents: six self-contained lenses (correctness, security, data/persistence, testing, maintainability/API-contract, performance) plus an adversarial generalist, with an optional Codex cross-model pass when `codex` is installed and authed. Every finding must quote the exact line that proves it or be forced below the confidence gate — the same false-positive-killing rule the review army depends on. Merged findings land in a durable `REVIEW.md` beside the plan before any fix runs, so an interrupted fix pass resumes from the file. Fixes run as fix subagents clustered by file (no two agents touch the same file), decisions surface one at a time as prose, and — the point of the whole design — the full gauntlet runs **once** at the end instead of after every fix cycle. A post-fix red-team subagent verifies the fixes hold and catches what the lenses missed. Self-contained: depends only on git, the harness Agent/Workflow tools, and optionally the GitHub/GitLab CLI and Codex. No external service, no server, no gstack — it never reads gstack checklists or assumes gstack is installed. VERSION/CHANGELOG bumping is conditional on the repo already using those files, so it imposes nothing on repos that don't.
- **`/pln-pr` triggering is reinforced so a compound instruction doesn't bypass the review.** Dogfooding surfaced the gap: "put up a PR" routed to the skill, but "bump the version and open the PR" was executed literally — bump, push, `gh pr create` — skipping the whole review army. Two layers close it. The skill's own triggers now explicitly claim PR asks embedded in a larger imperative ("and open the PR", "push this up"), while still honoring an explicit "skip the review". And a new opt-in global routing rule, installed via the consented preview-and-approve pattern (never automatically), tells the host to route every open/create/put-up-a-PR request through `/pln-pr`. The rule ships through a small idempotent helper, `bin/pln-routing-rule` (`--plan` previews, apply is a no-op if already present, writes to the user's global `~/.claude/CLAUDE.md` or `~/.agents/AGENTS.md`). `setup` offers it once at the end of a fresh install; `/pln-update` offers it once to existing users who upgrade without it; both gate on a `routing_prompted` marker so it never nags, and neither writes a single line without a yes.
- **`/pln-pr` was hardened after dogfooding it on its own PR (a `/pln-pr` self-review).** The routing helper now refuses to write without an explicit `--apply` and centralizes the offer text and gate behind a single `--offer` mode both call sites relay. The review flow was made fail-closed (an empty reviewer set stops rather than passing as "clean") and injection-safe (refs and PR bodies never interpolate into the shell). Note: existing users receive the routing offer on their *next* `/pln-update` after upgrading, not on the upgrade that installs 1.14.0 — a one-release delay that self-heals on the following run.

### Added

## 1.12.0 — 2026-07-08

### Changed

- **Step 5 now runs one Workflow script per implementation run instead of one Workflow invocation per item, in both interactive and auto mode.** Previously the orchestrator called Workflow once per item and waited for each item's notification before spawning the next; auto and interactive mode used the same mechanism but neither exploited Workflow's own resumability. Now the orchestrator builds a single script covering every pending item — the per-item loop lives inside the script, not in the orchestrator's own context — and invokes it once. On a blocker in interactive mode, the script returns immediately with the blocking question instead of trying to spawn a follow-up call itself (a running script has no channel back to the user mid-run); the orchestrator asks the user, records the answer, then resumes the same run via `resumeFromRunId` with the answer folded into `args`. Auto mode is unaffected in spirit — the script just doesn't stop on a blocker — but now shares the same one-script-per-run shape and gets the same resumability for free. Confirmed empirically: a script that deliberately returns early replays its completed prefix from cache on resume and continues past the return point, verified against the journal (no new `started` event for the already-completed step).
- **Auto-mode ⏸ blocked items now resolve at Step 6 through the same resume mechanism as an interactive blocker**, rather than being folded into the "revisit / push / drop" prompt used for deferred items. Each blocked item already has a concrete question recorded in its handoff file; Step 6 asks it directly and resumes the run.
- **The pending-item list for a run is now built fresh from `PLAN.md`'s status column, not carried as an in-memory cursor.** Guards against re-spawning an already-✅-done item if the orchestrator itself (not the Workflow run) gets re-invoked after an interruption.

### Fixed

- **`args` passed to a Workflow script arrives as a JSON string, not a parsed object.** Documented as a failure mode: any script logic that branches on an `args` field (as the new blocker-resume flow does) must `JSON.parse(args)` first, or the field reads as `undefined` silently. Discovered empirically while confirming the resumability behavior above.

## 1.8.0 — 2026-07-02

### Fixed

- **The update check now scans every installed copy instead of stopping at the first one.** pln can be installed in more than one root at once (`~/.agents`, `~/.claude`, `~/.codex`, plus project-local variants), and the host often loads a different copy than the one that sorts first. The old check ran the version check from the first directory it found and stopped there, so a current `~/.agents` copy could mask a stale `~/.claude` copy — the one Claude Code actually loads — and report "up to date" while the running skill was two versions behind. `bin/pln-update-check` now reads the VERSION of every installed copy and reports `UPGRADE_AVAILABLE` whenever any copy is behind remote, using the lowest version as the baseline. A new `bin/pln-update-apply` helper upgrades every copy in one pass (git installs via fetch + reset, vendored installs via a single re-clone), skips developer symlinks, rolls back a failed vendored copy, and prints a per-copy summary. The subagent and its brief are unchanged; only the spawn mechanism changes. This makes the subagent's live tool calls visible by selecting its row in `/workflows` while it runs, with none of that activity landing in the orchestrator's context — previously, a backgrounded item's work was completely invisible until it returned. Verified by hand: confirmed `/workflows` updates live (token/tool counts) and that selecting a running agent's row surfaces a live Activity feed of its actual tool calls, not just a status counter. Because Workflow replies via a task-notification instead of a synchronous return, the orchestrator now waits for that notification before spawning the next item, preserving the existing one-item-at-a-time sequencing. The orchestrator also now tells the user once, before the first item spawns, that `/workflows` is where to watch live progress.

## 1.3.0 — 2026-06-24

### Changed

- **The implementation phase runs autonomously through per-item subagents.** Once the master plan is adopted, the main session becomes a thin orchestrator: it walks the items in order and spawns a fresh general-purpose subagent for each one, sequentially, with `PLAN.md` as the entire spec. The orchestrator never reads code or edits files itself, so its context stays light across the whole run and every item gets the blank-slate context a fresh session used to provide by hand. The subagent brief carries every per-item concern — mandated-skill invocation, lightweight verification, the commit, and memory capture — because the orchestrator is no longer doing that work. End-of-task verification also runs in a subagent so the gauntlet's stdout stays out of the orchestrator's context.
- **Blocker protocol replaces the pause-and-ask thresholds.** A subagent can't ask the user anything, so the four mid-item-discovery thresholds become a stop-and-hand-off protocol. On hitting one, the subagent leaves its work uncommitted, writes a transient handoff file (`<timestamp>-item-<N>-<slug>.md`) describing what it did and the self-contained blocking question, and returns `BLOCKED:`. The orchestrator surfaces the question one-at-a-time, records the answer in `PLAN.md`, then spawns a fresh subagent that reads the handoff file and the uncommitted diff and resumes from where the first stopped — no work thrown away. A subagent commits only a complete, verified item, never partial work. Auto mode now means the orchestrator defers blockers (partial work stashed, item marked ⏸ blocked) to the end-of-run review instead of surfacing them immediately. ## 1.1.0 — 2026-06-10

### Changed

- **Interview asks only what only the user can answer.** Every open choice now routes through a filter with two checkable tests — *authority* (can you cite a concrete source that already decides this, by name?) and *reversibility of consequence* (can you name what would have to depend on it before it could change?). Unbacked-and-consequential choices become one-at-a-time interview questions; cite-backed or reversible choices are decided and disclosed; not-yet-knowable choices are deferred to implementation. This narrows the interview to the user-owned decisions and stops the indifferent-bare-letter answers that signalled a wasted question.
- **Disclosed-decisions list at the master-plan gate.** Decide-and-disclose calls are presented at Step 4 as a globally-numbered, item-grouped, **self-triaged** list — the few low-confidence calls flagged for review, the rest scannable. The user reopens any by number ("3, 7, 8") to drop back into the one-at-a-time interview, starting from the recorded position and its rationale; unlisted decisions stand as accepted.
- **One filter, two surfaces.** The same tests govern what the plan *prescribes*. `PLAN.md` records intent, constraints, acceptance criteria, and load-bearing/irreversible decisions at full fidelity, but no longer prescribes reversible implementation mechanics (sequencing, internal structure, exact commands) — those are left to the implementer. Decisions are recorded as overridable-when-reversible context, not imperative steps; guardrail boilerplate ("remember to test") becomes a stated qualitative bar. Plans read as goals, not step lists — better for capable implementers (Opus or Fable) without branching on the active model.
- **Plain conversational voice.** A new Style rule strips Claude's default "intense, over-confident tech bro" register from the skill's prose: minimal bold, no em-dash drama, no certainty-theater words ("load-bearing", "the crux", "exactly right"), claims stated once instead of as "not just X, it's Y", no agreement-amplifier openers, no restating the user's point back, no pre-labeling a point as significant ("it's a real fork") or announcing a question before asking it, no self-congratulatory adverbs ("cleanly", "elegantly"), no jargon or strained metaphors where a plain word works ("load-bearing", "moves the needle", "the rule that would bite"). Also leads with the answer instead of burying it under narrated reasoning, and matches response length to the question. Governs conversational prose only; the functional formatting (option labels, `[recommended]` marker, status icons, numbered sequences) is exempt. `/plnify` now installs a matching **Plain voice** section (its third) so gstack planning skills get the same register.
