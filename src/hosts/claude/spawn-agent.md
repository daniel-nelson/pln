Use the harness's own agent primitives. Same-provider work stays native; nothing here shells out while the current tools are available.

- **One fresh worker that may need another turn:** call `Agent` with a non-fork `general-purpose` subagent, complete prompt, stable `name`, and background execution. This **directly addressable background Agent** starts fresh and reports a completion notification; retain its ID and name. Fork mode may make background execution implicit; the invariant is unchanged.
- **Continue or steer an Agent:** use `SendMessage`, addressed by agent ID (preferred) or the stable name. A message sent after completion auto-resumes that same subagent in the background; a message sent while it is running steers the current turn. Wait for the next completion notification. An agent message never substitutes for user approval or changes permissions.
- **Several independent workers in a true fan-out:** use `Workflow`: `agent(prompt, { label, schema })`, or `pipeline(items, item => agent(...))` in parallel. It is for independent review/research, not the sequential implementation loop: it has no mid-run user channel. Resume a stopped run from `/workflows` or relaunch the script; never invent a tool-only run-id.
- **Workflow input:** saved workflow `args` is structured data and is read directly. Do not stringify it and do not parse it. If omitted it is `undefined`.
- **Non-empty results:** a foreground Agent returns one final text result; a background Agent reports that result in its completion notification. A successful notification with no result, an API-error termination, or a Workflow `agent()` result of `null` is a failed worker, not an empty finding set. Structured Workflow results use the `schema` option when needed.
- **Watching work:** named background Agents appear in `/tasks` and the session's agent UI. Workflow fan-outs appear in `/workflows`. Those views expose live activity without loading the worker's reasoning trace into the coordinator.

**No shell keepalives.** Await a background Agent or Workflow through its native completion notification or tracked handle. Never launch idle Bash merely to keep the parent turn open—no `sleep`/impossible-condition loop, `tail -f`, or dummy process. If native waiting is unavailable, run the Agent or Workflow in the foreground or sequence the work; do not synthesize a shell keepalive.

**When native Agent is unavailable — the fallback.** A current Claude Code install has `Agent`; an older or policy-disabled host may not. Disclose the fallback, then use `{{SKILL_DIR}}/bin/pln-claude-agent` with the same on-disk brief. It defaults to a read-only peer tool set; implementation fallback deliberately widens it with `--tools Read,Grep,Glob,Edit,Write,Bash`, while reviewers keep the default. The helper enforces stdin briefs, a timeout, no MCP servers, truthful non-zero/empty failure, and file-first output. It is one-shot and nonpersistent: if it blocks, launch a fresh fallback worker pointed at the handoff, the recorded answer, and the existing diff rather than pretending a vanished native handle can resume. This nested CLI path is also the cross-provider route used by `pln-peer`; it is never preferred over a usable native Agent.
