Once the schedule is validated, the main session is a thin coordinator: it owns the manifest, `PLAN.md`, git checkpoints/integration, and user interaction, but never item implementation. Use directly addressable Agents rather than Workflow: a blocked worker must be able to accept another turn, and a cohort continuation is another turn on the same worker.

**Native Agents are the mechanism, not one option among two.** Where the host exposes them — it normally does, and this run has already used them for research and review — dispatch item work through them. `pln-claude-agent` exists for a host that genuinely lacks them or a policy that forbids them, and taking it is a decision to disclose with its reason, not a branch to drift into. A run that has spawned native agents successfully in an earlier phase has its answer.

Before the first item, tell the user once where to watch: each item runs as a named background Agent, and its live activity — the actual tool calls, as they happen — is visible in `/tasks` and the session's agent UI under that name. That view costs the coordinator's context nothing, so it is the way to watch without derailing the run. Name each worker after its item (`item-3-metrics`, not an opaque handle), so those rows read as the plan's items. On the `pln-claude-agent` fallback, say instead that item work will not appear there, and why.

Item work happens in the working tree the run was launched in. Do not create a git worktree, and do not pass `isolation: "worktree"`: a fresh worktree is a bare checkout with no installed dependencies, environment file, database or port block, and every worker handed one rebuilds that for itself — none of which git tracks, so no lease describes it and no dirty snapshot protects it.

For each item `pln-scheduler ready` names:

1. Launch one stably named non-fork `general-purpose` Agent, in the source tree, with its one-item brief. Record the returned Agent ID and `running` state in the manifest. One worker owns the tree at a time; never overlap it with another writer.
2. Wait for its completion notification. A failed/API-error notification, empty result, malformed envelope, or write outside the lease fails that node; preserve its artifacts, mark the manifest, and force a fresh boundary. A blocked worker follows the blocker phase.
3. The coordinator validates the result and diff, stages only the leased paths, and creates the item commit with the required co-author trailer. Workers always receive `commit owner: coordinator` and never touch git or `PLAN.md`. Record result, actual route, commit, and `checkpointed` status immediately.
4. Integrate, after dirty-state validation, then update `PLAN.md` and mark the node integrated. A conflict, unexpected write, corrected premise, or dirty-state mismatch stops integration and forces a fresh worker boundary after reconciliation; never resolve it by letting a cohort continue on the old premise. Where the integrated item changed dependency declarations, re-sync the environment to the tree before releasing the next item.
5. When the next item is a `reuse` node in the same cohort and its predecessor is checkpointed, `SendMessage` that Agent ID with a new one-item brief. This is another Agent turn after a durable item checkpoint, not one multi-item prompt. Otherwise start a fresh Agent.

Persist an interruption before acting on it: mark the affected manifest node `interrupted`, record the last durable result, then steer a still-running Agent with `SendMessage` or stop it through the host UI. Integrate nothing unfinished. Recovery may continue a retained ID or start a fresh Agent on the item and its handoff/result when the ID is gone.

On a host without native Agents, disclose the fallback and run fresh workers serially through `pln-claude-agent`. It cannot preserve cohort continuity, so say that rather than claiming it.
