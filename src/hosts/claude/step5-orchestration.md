Once the schedule is validated, the main session is a thin coordinator: it owns the manifest, `PLAN.md`, git checkpoints/integration, and user interaction, but never item implementation. Use directly addressable Agents rather than Workflow: native Agent isolation supplies separate git worktrees, and a blocked worker must accept another turn.

For each ready manifest wave:

1. For an `isolated` node, launch a stably named non-fork `general-purpose` Agent with `isolation: "worktree"`, background execution, and its one-item brief. Record the returned Agent ID, native worktree path, and `running` state in the manifest before launching the next member. If this host does not expose a durable worktree path, do not parallelize: rebuild that node as a fresh original-tree serial fallback. For an `original` node, run one Agent at a time in the source tree and never overlap it with another writer.
2. Launch every disjoint isolated member of one wave before waiting. Wait for all completion notifications. A failed/API-error notification, empty result, malformed envelope, or write outside the lease fails that node; preserve its artifacts, mark the manifest, and force a fresh boundary. A blocked member follows the blocker phase. Successful siblings may be validated and checkpointed in their own worktrees, but not integrated across a blocker.
3. The coordinator validates each result and diff, stages only the leased paths in that node's worktree, and creates the item commit with the required co-author trailer. Workers always receive `commit owner: coordinator` and never touch git or `PLAN.md`. Record result, actual route, commit, and `checkpointed` status immediately.
4. Integrate checkpointed commits into the source worktree strictly by manifest integration order, after dirty-state validation, then update `PLAN.md` and mark each node integrated. A conflict, unexpected write, corrected premise, or dirty-state mismatch stops integration and forces a fresh worker boundary after reconciliation; never resolve it by letting a cohort continue on the old premise.
5. When the next ready item is a `reuse` node in the same cohort, its predecessor is checkpointed, and the retained Agent/worktree are intact, `SendMessage` that Agent ID with a new one-item brief. This is another Agent turn after a durable item checkpoint, not one multi-item prompt. Otherwise start a fresh Agent. Stop reusing after three cohort nodes.

Persist an interruption before acting on it: mark each affected manifest node `interrupted`, record the retained worktree and last durable result, then steer a still-running Agent with `SendMessage` or stop it through the host UI. Integrate nothing unfinished. Recovery may continue a retained ID or start a fresh Agent on the item, handoff/result, and worktree when the ID is gone.

On an older/disabled host without native Agent isolation, disclose the fallback and run fresh workers serially in the original tree through `pln-claude-agent`. The fallback never claims concurrency or cohort continuity it cannot durably preserve.
