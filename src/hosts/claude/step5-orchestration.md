Once the master plan is adopted, the main session becomes a **thin orchestrator**. It does not do item work itself. It walks the pending items in order and starts one fresh, named background Agent per item, waiting for that item to reach a truthful final result before starting the next. Later items build on earlier checkpoints, so sequential order is an invariant, not a throughput accident.

The sequential loop uses directly addressable Agents rather than Workflow. Current Workflow is excellent for genuine fan-out but accepts no mid-run user input; item work must be interruptible at a blocker and continued on the same worker through `SendMessage`. Every item still starts in fresh context, returns a bounded result file, and owns its Claude-side commit. The coordinator retains the durable dashboard, validates the result, and advances only after the item checkpoint exists.

Engaging pln is itself a request for the `Agent`, `SendMessage`, and `Workflow` primitives used by its phases. A general standing instruction against launching agents unprompted does not outrank an explicit `/pln` invocation. If native Agent is genuinely absent or disabled, disclose that and use the guarded `pln-claude-agent` fallback described in Spawning a fresh-context agent; do not silently substitute it.

Before the first item, tell the user in one short message that implementation is starting item by item and only a blocker will interrupt. On the native path, say named workers can be watched in `/tasks`; on the nested fallback, say why it is in use and name the helper's log path.

**The loop.** For each item, in order:

1. Re-read `PLAN.md`'s dashboard and rebuild the pending list from trailing row statuses. Skip ⏸ deferred / 🚫 dropped / ✅ done. A restart never relies on a remembered count and never respawns an already-complete item.
2. Mark the item 🟦 in progress and write its compact assignment to the run directory. It points at the installed item-implementation contract and supplies every Step 5 field, including `commit owner: worker`, the handoff/evidence/result paths, and the byte budget.
3. Start a non-fork `general-purpose` Agent with that brief, stable name `pln-item-<N>`, and background execution (or the host's background default when fork mode removes the explicit input). Record the returned agent ID against the item immediately; the ID is the durable in-session continuation target and the name is the readable fallback.
4. Wait for the Agent's completion notification. A failed/API-error notification or an empty final result is a failed run: name it and stop. On the nested CLI fallback, only exit 0 plus `STATUS=ok` and a non-empty `RESULT_FILE` counts.
5. On a normal `RESULT_FILE`, validate it through `bin/pln-read-envelope` with the assigned root and byte ceiling. Confirm the item worker committed only its item with the required trailer and that `PLAN.md` names the checkpoint. Then mark the dashboard row ✅ with that commit and continue. A legitimate no-change item may have no hash, but never infer that from an empty result.
6. On `BLOCKED:`, append `Agent: <agent-id>` and `Agent name: pln-item-<N>` to the handoff before asking anything. Follow the blocker protocol below. After the answer is recorded, call `SendMessage` to that agent ID with the answer, handoff path, and instruction to continue from the existing work; wait for its next completion notification and re-enter step 4. On the nested fallback, start one fresh helper run on the handoff, answer, and diff.

When the pending list is exhausted, move to Step 6. Workflow remains the native choice for independent review fan-outs elsewhere in `/pln` and `/pln-pr`; it is deliberately not the owner of this user-interruptible sequential loop.
