**Why this backgrounds as a shell process, not a native subagent.** The natural instinct is to hand the poll loop to a native subagent the way every other fresh-context job in this skill runs — but a spawned agent inherits the orchestrator's sandbox with no network (the same reason `pr-host-note` and Step 8's codex note already give for why the orchestrator itself runs every `git`/`gh`/`glab` call), and `gh pr checks` needs the network `gh` itself needs. A child that can't reach GitHub can't poll it. So the poll loop has to run from the orchestrator's own shell, which does have network — and to keep it from being a blocking foreground wait, it backgrounds as a detached process from that same shell, the same sandbox this skill's gauntlet runs already live in (Steps 2/7's caveat): `( poll-loop-with-the-interval-math-above ) > "$RUN/watch.log" 2>&1 & disown`. That single line is the shell fallback this step needs, said plainly rather than left implicit — the fix-agent dispatch below is not part of that fallback, and stays native.

**Picking the result back up.** Codex's `notify` hook fires only at this session's own turn completion and cannot be aimed at an external background job finishing, so nothing pings you the instant that detached process reaches a terminal state — read `$RUN/watch.log`'s tail whenever this step next gets a turn (the same turn if the loop was quick, a later one if the user comes back to it, or a scheduled `/pln-pr` re-check) and act on whatever terminal line is there. Never read the whole log into your context — the tail is the only part that matters, same discipline as every other log this skill produces.

When the tail shows a terminal state:

- **Green** — undraft and record the duration as described above, then fire the completion notification.
- **Red** — build the finding, write it into `REVIEW.md`, then dispatch the one fix cluster natively, the same way Step 4 already does: `spawn_agent` with a fresh context, `wait_agent`-looped to completion, per Spawning a fresh-context agent and `pr-fix-invoke` — including its `BLOCKED:` handling. This part needs no shell fallback; a fix agent only writes files and needs no network. Once it returns and its commit is pushed, relaunch a fresh detached watch process for the next round — don't try to make one background process survive across a fix commit.

Track the same-check streak and the `BLOCKED:` case across rounds in the orchestrator's own context (this session, not the background script) — that bookkeeping is what decides when to stop instead of relaunching another round.
