**Wave width: up to 3 item workers at once.** Where the session states its concurrency slot count, the width is that count less one for the coordinator. Otherwise, where `~/.codex/config.toml` sets `max_concurrent_threads_per_session` (the older `agents.max_threads` is an alias for it), use its value less one; read it once, in the same shell call that opens the phase. Otherwise the width stays 3: the unset default is documented inconsistently — four *including* the root in one place, six in another — so three is the widest wave that stays inside either reading, and it is also where the practitioner consensus on reconcilable concurrent results sits. A plan with more active items runs in successive waves, each awaited whole before the next is dispatched.

A spawn refused for capacity while workers of this wave are known finished means a finished child is still holding its slot: free the finished workers' slots and retry that spawn, rather than reading the refusal as a hard ceiling and falling back to one worker at a time.
