Once the schedule is validated, the main session is a thin coordinator: it owns the manifest, `PLAN.md`, every git checkpoint/integration, and user interaction, but never item implementation.

**Native agents are the mechanism, not one option among two.** Where `spawn_agent` is available — it normally is, and this run has already used it for research and review — dispatch item work through it. `pln-codex-agent` is for a host that genuinely lacks native collaboration or has it switched off, and taking it is a decision to disclose with its reason, not a branch to drift into. A run that has spawned native agents successfully in an earlier phase has its answer. Observed otherwise: a coordinator that used `spawn_agent` fourteen times without a failure read this phase, ran `pln-codex-agent --help`, and then put every item, verification and repair through nested subprocesses that share one authentication state and therefore cannot overlap — serializing work it had already been told was ordered anyway, and paying a fresh process, a fresh context and a full re-read of the plan and root instructions for each one.

Item work happens in the working tree the run was launched in. Do not create a git worktree: a fresh worktree is a bare checkout with no installed dependencies, environment file, database or port block, and every worker handed one rebuilds that for itself — none of which git tracks, so no lease describes it and no dirty snapshot protects it.

For each item `pln-scheduler ready` names:

1. Spawn one agent with `fork_turns: "none"`, a stable task name, and a one-item brief naming its lease. Record the returned agent identity and `running` state. One worker owns the tree at a time; never overlap it with another writer.
2. Wait through the bounded mailbox loop until it is complete, blocked, or failed. Run `list_agents` after every quiet timeout before waiting again; a completion can land between waits and must be consumed immediately.
3. A failed agent, empty result, malformed envelope, or write outside the lease fails that node; preserve its artifacts, mark the manifest, and force a fresh boundary. A blocked worker follows the blocker phase.
4. The coordinator validates the result and diff, stages only explicit leased paths with `git add -- <paths>`, and creates the item commit with the required co-author trailer. Workers always receive `commit owner: coordinator` and edit neither git nor `PLAN.md`. Record result, actual route, commit, and `checkpointed` status immediately.
5. Integrate, after dirty-state validation, then update `PLAN.md` and mark the node integrated. A conflict, unexpected write, corrected premise, or dirty-state mismatch stops integration and forces a fresh worker boundary after reconciliation. Where the integrated item changed dependency declarations, re-sync the environment to the tree before releasing the next item.
6. When the next item is a `reuse` node in the same cohort and its predecessor is checkpointed, use `followup_task` on that idle identity with a new one-item brief. This is another turn after a durable item checkpoint, never one uncheckpointed multi-item prompt. Otherwise spawn a fresh agent.

Persist an interruption before acting on it: mark the affected manifest node `interrupted`, record its last durable result, then use `send_message` for a steer or `interrupt_agent` for a real stop. Integrate nothing unfinished. Recovery may use `followup_task` on a retained identity or spawn a fresh agent on the item and its handoff/result when the identity is gone.

On a host without native collaboration, disclose the fallback and run fresh workers serially through `pln-codex-agent`. It cannot preserve cohort continuity, so say that rather than claiming it.

**Manifest-backed turn boundary.** Never send a final response from `Phase: implementation`. Before changing to `Phase: finish-ship`, first call `list_agents` and reconcile every known native child, then run `{{SKILL_DIR}}/bin/pln-scheduler finish-check --manifest <plan-dir>/run-manifest.tsv`. `STATUS=active` (exit 3) means the turn stays alive: consume a completed child, integrate a checkpoint, recover the named item, or wait again. Only `STATUS=complete`, with no running child, permits the phase transition. A genuine user-owned blocker is not an exception inside this phase: persist its handoff/status, change to `Phase: blocker`, and only then ask its one necessary question. A timeout is another reconciliation-and-wait cycle, never a reason to summarize and end the turn.
