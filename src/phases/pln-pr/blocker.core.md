# /pln-pr phase: blocker handling

<!-- pln:include active-turn-lifecycle -->

Read this file in full before the first blocker action. `REVIEW.md` plus `fix-manifest.tsv` must name the finding/cluster, self-contained question, available handle or fallback result, partial working-tree state, checkpoint state, and expected continuation. A handle may be lost; a handoff may not. Missing or contradictory recovery state fails closed.

Every answer, recovery fact, and cursor change is written into a complete next-generation candidate and published through `{{OUTPUT_ROOT}}/bin/pln-publish-review` with the current digest/generation. Never edit canonical `REVIEW.md`; a stale rejection requires rereading and reconciling the blocker state.

Freeze new dispatch; clusters run one at a time, so nothing else is running to checkpoint across the blocker. Ask at most one durable question. After the answer, write it against the finding, reconcile the exact tree, set `Phase: fix`, then read the fix phase in full before same-agent continuation, documented fresh-worker recovery, or first dispatch of a needs-decision cluster that had no worker yet. If the blocker invalidates scope/base/trust, record that fact and return conservatively to `scope-baseline`. Auto mode is `{{PLN_CMD}}`-only.

**Repair-decision window.** A production-reachable `worker-blocked` handoff for a consequential repair, or a `needs-decision`/`destructive` finding with an already selected repair, uses this window when the repair does not contravene an explicit owner constraint. Record its exact candidate and selected repair. In the staged ledger record `Decision asked at` as `date +%s` and `Decision reminded at: none` before the first question. Fire enabled notifications before the question ({{NOTIFY_CALL}}). **The question is a message the user can read, sent before the clock starts:** the complete option message, through the host's asynchronous question surface if available, otherwise a nonterminal assistant message, keeping this parent turn active. A notification, a ledger entry or a pointer to either is not the question. Word it as the run's pick with a window to change it, not as a call only the user can make: name the repair it will build and the clock time it starts, the other options as switches with both `fix` and `smaller_fix` and their consequences, and that one reminder follows in five minutes. Notifications say the same — the pick and its start time, never that the repair needs the user's call. A final answer would cancel the timer. A user reply always takes priority over a timeout, including one that arrives as a wait returns. A request for an example is not an answer: give it as Style's example option describes, then restart the window from the question it ends with, publishing a new `Decision asked at` and `Decision reminded at: none`.

While that question is open, use `{{OUTPUT_ROOT}}/bin/pln-decision-window --asked-at <recorded epoch> [--reminded-at <recorded epoch>]` to check the deadline. On `STATUS=wait`, wait with a host-native interruptible timer when available, otherwise `sleep` for at most 30 seconds, capped by `WAIT_SECONDS`; then check for a user reply before checking the deadline again. Timer checks, quiet waits, and the reminder's publication and notification are the exceptions to Active-turn lifecycle's no-tools-while-a-question-is-open rule: do not read worker results or dispatch work. On `STATUS=remind`, re-check for a reply, publish `Decision reminded at` as the current `date +%s`, fire enabled notifications again, and repeat the same self-contained question with its new five-minute deadline. On `STATUS=proceed`, re-check for a reply, then publish `Decision: standing timeout authorization` with the selected repair, candidate, both recorded epochs, and no-answer observation; set `Phase: fix` and continue the idle worker (or its fresh recovery) with that exact authorization. Never infer `proceed` from a failed helper, a lost clock, a wait the host refused, or a final response. If the run is interrupted, reconcile the ledger and continue from its recorded timestamps; a reminder that was never sent must be sent before its second five-minute window begins. A later answer is steering for the active repair and is recorded before the next action it can still change.

Observed: a run wrote its question into `REVIEW.md`, notified that the repair needed the user's call and would proceed in ten minutes, and told the user the question was open above when no message had carried it. The host's permission check then refused the timer that would build past it, and the run stopped with nothing built while its user was away. A refused wait authorizes nothing by another route; the question stays open.

An explicit owner constraint, a missing or changed candidate, or a question with no selected repair does not acquire timeout authorization. A timeout never lifts an owner constraint. Handle these through the ordinary answer and recovery path above.
