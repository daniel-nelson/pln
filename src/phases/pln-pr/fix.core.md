# /pln-pr phase: fix

<!-- pln:include active-turn-lifecycle -->

Read this file in full before the first fix decision or dispatch. Rebuild open clusters from `REVIEW.md`, not memory. **A change the user asks for during this phase becomes a cluster of its own**, recorded in `REVIEW.md` with its finding text and dispatched to a fresh worker like any other — not typed into the tree by the coordinator, whose job here is to brief, validate, commit and integrate. It is item work whoever asked, a one-line request included, and the coordinator that edits product files itself both loses the fresh-context guarantee and fills with the diffs and test output of every follow-up. **This phase carries its fix-worker and verifier briefs inline, below — there is no separate contract file for a fix or a post-fix verifier.** The post-fix merge is the exception: it runs on the first merge's `pr-review-merge.md`, named in Step 5. Searching `src/workers/` for any other contract of this phase finds nothing and costs a round trip, which a real run spent. `execution-schedule.md`, `behavior-preservation.md` and `pr-review-merge.md` are the only contracts this phase names, and each is named where it applies. Keep the cursor here while fixes and their narrow verification/checkpoints complete.

Every coordinator ledger update in this phase—decisions, checkpoints, integration status, post-fix merge, repair attempts, settled candidate, blocker cursor, and ship cursor—is a complete staged candidate published through `{{OUTPUT_ROOT}}/bin/pln-publish-review` with the current digest/generation. A post-fix merge/verifier writes only its assigned candidate path and bounded envelope. Never let a worker or direct edit touch canonical `REVIEW.md`; stale publication means reread and reconcile.

Before asking a decision or handing off a blocked cluster, write it and all partial-state pointers durably, then set `Phase: blocker` and load that phase. Once every finding is durably fixed/skipped and the post-fix result is recorded, set `Phase: ship-watch` and load that phase before versioning, the final gauntlet, push, PR, or CI work.

### Step 4. Fix pass — clustered fix subagents

Classify each acted-on finding as **auto-fix** (mechanical, unambiguous — a null check, a missing timeout, a spec for uncovered behavior) or **needs-a-decision** (a judgment call — a design change, a tradeoff, anything where the fix isn't obvious or is destructive).

A structural consolidation uses the same routes. The single behavior-preservation owner is `{{SKILL_DIR}}/src/workers/behavior-preservation.md`; every fix worker handling a removal, replacement, or consolidation reads and applies it before editing. Before classifying or dispatching automatic work, validate the finding's complete `Safety disposition` from `REVIEW.md` against that owner. A missing or malformed record is `retain`, as is any missing, failed, unknown, empty, incomparable, or contradicted conjunct. Only a complete `admit` record with every conjunct `pass` may proceed to automatic work, and public, compatibility, persisted/stateful, consequential, or destructive work remains destructive/needs-a-decision even when its behavioral proof is complete. Structural clues cannot override the disposition.

Before editing, the worker validates the admitted baseline record and reruns the same admitted behavior suite on the actual pre-change source; afterward it reruns that suite under equivalent inputs and environment. Existing behavior-oriented tests are primary; implementation-detail or post-only tests may supplement, never replace, that common boundary. Automatic deletion still requires private reachability, bounded consumer closure, and repository-native discovery, but those facts do not replace behavior proof, and evidence that falls short of it retains the surface or becomes destructive/needs-a-decision on the same terms as above. The full repository gauntlet remains the final regression floor in Step 7. No similarity score, raw-growth threshold, deletion target, or cleanup quota can authorize a simplifying mutation.

**A finding the ledger records as `reached_by: test-only` is never one of these questions**, and never a blocker, whatever surface its proposed fix would touch. Repair it automatically where the ordinary rules already allow that, and otherwise retain it and file the follow-up. The decision routes above exist for defects the shipped system can reach; spending one on a state only the test suite constructs buys a design the user did not ask for, aimed at a failure that cannot occur.

**Nothing reaches this phase that is not work.** A finding whose named consequence did not survive the merge worker's check against the source was dropped there, by that worker, and no trace of it arrives here — the fix phase has no preference queue to skip, because the decision was made once by the only reader in a position to make it. Do not reconstruct one. If you find yourself reasoning that a finding is minor but the repair looks cheap, the finding is a defect and the repair is cheap; a cheap repair is not a reason to build something and never was.

For needs-a-decision findings, surface them to the user **one at a time**, as prose, in the option-message shape, fire notifications first. **The question carries the finding's `smaller_fix` beside its proposed fix** — which smaller repair was passed over and why it lost, or that the reader found none — because a question that presents one design as the only way to close a defect asks the user to ratify the design rather than decide the tradeoff, and the reader already did the looking. A `none found` the finding's own citations contradict is worth saying so about in the same message. Record each answer in `REVIEW.md` against its finding. A skipped finding is marked `skipped`; it becomes a follow-up in the closing message's bullet list only if it clears the follow-up bar (Style's "Ending a message") — someone will actually need to act on it or decide about it later. A skip that was really "not worth doing" gets no follow-up entry.

A fix worker that returns `BLOCKED:` because its repair would add a persisted-state write or transition, an external effect, or a public export (its brief's stop, below) is `worker-blocked`, and its question takes this same shape with both repairs in it. That stop is the only thing that narrows the standing repair authority in Step 5; a test-only finding it leaves unbuilt is retained and filed, as above.

Before dispatch, snapshot the source tree and build `<plan-dir>/fix-manifest.tsv` with `bin/pln-scheduler`. **A single cluster is not a scheduling problem: write its one-node artifact directly and skip the worker.** With one node there is no order to derive, no cohort boundary to place, and the lease is the cluster's own declared file set, which the ledger already holds — so a fresh `judgment` worker there costs minutes of frontier effort to answer a question with one possible answer. Observed: a one-file consistency fix waited 3.6 minutes for a scheduling worker before any work began. With two or more clusters, send the resolved cluster list to a fresh `judgment`-profile worker on `{{SKILL_DIR}}/src/workers/execution-schedule.md` in `pr-fix-clusters` mode and validate its envelope: dependencies, overlapping/ancestor leases, generators, lockfiles, tests, configuration, migrations, and shared effects add edges, unknown means serial, and none of that is the coordinator's to invent. Independent clusters start fresh; clusters the schedule had to order may share a worker under the cohort boundaries. Execution is linear either way — one cluster at a time, in the working tree the run was launched in. `REVIEW.md`, the manifest, git checkpoints, and integration are coordinator-only. Auto mode never applies to `{{PLN_PR_CMD}}`.

### Step 5. Post-fix assurance

Every fix creates a new candidate; recompute its exact fingerprint before assurance. R1 narrowly verifies the finding and targeted tests. R2 runs one fresh post-fix verifier across the fixes and specialist risks. R3 runs a full fresh red-team pass after nontrivial fixes; this is separate from the four-reader pre-fix cap. A trivial R3 fix still gets a fresh verifier plus explicit evidence for why a full red team was unnecessary — the coordinator validated the fix and may not also certify that no deeper review was needed, which is the whole reason that reader is fresh.

**That verifier judges; it does not rebuild what the fix already proved.** Where the fix worker's validated result carries regression-first evidence for this same candidate — the failure the new test produced before the change, the exact command and count after it — and the recomputed fingerprint matches the one that evidence was produced under, the verifier rules on triviality and residual risk from that evidence, the bounded diff, and the recorded structural checks. It reruns a suite only where the evidence is absent, incomparable, or produced under a different fingerprint, and names which of those applied. Independence is in who judges, not in who re-executes a passing test: a fresh reader that rebuilds the review, the repository and its own context in order to re-run tests the fix worker ran minutes earlier spends its whole cost before reaching the judgment it exists to make. Observed: 3.6 minutes on a two-file, one-line follow-up, ending in the same 27/27 the fix worker had already recorded.

At the repair's semantic risk tier, every post-fix path must rerun the structural reference check and consumer map (including direct and indirect consumers) for each structural finding and compare the recorded before/after owners, paths, and knobs. For a removal, replacement, or consolidation, it also rechecks repository-native discovery, bounded closure, and the post-change result from the same admitted behavior suite against its actual pre-change outcome under `{{SKILL_DIR}}/src/workers/behavior-preservation.md`; deletion additionally rechecks private reachability. Missing, changed, flaky, or incomparable proof reopens the same structural repair key and fails closed; do not treat passing post-change or implementation-detail tests alone as structural assurance. Step 7 still runs the full repository gauntlet once after assurance is clean.

The R3 red team writes complete findings to `<plan-dir>/evidence/post-fix-red-team.json` and returns only that pointer. Give it the verified findings/fixes and exact candidate fingerprint:

"Read the exact post-fix candidate. Reproduce the listed fixes and hunt for missed cross-cutting failures or regressions. Where the assignment names a `Settled candidate`, your scope is exactly `git diff <Settled candidate> <candidate commit>` — what those repairs broke, and what they newly let a reproduction's input reach — and not the rest of the candidate. Write only findings with exact citations and runnable reproduction/test evidence; label unsupported suspicions unverified. Give each finding a `reached_by`: the exact non-test `file:line` that can put the shipped system into the state your reproduction constructs, or `test-only`. Give each finding a `breaks_if_shipped`: the observable failure a consumer meets if this merges unchanged, or the literal `nothing` when what you found is that it could have been built differently. Give each finding an `on_base`: the diff-base `file:line` that already fails this way plus the base non-test caller that reaches it with your reproduction's same input and the same consequence, read with `git show "<diff-base>":<path>`, or the literal `branch`. Return only the assigned `RESULT_FILE` pointer."

Never open that reviewer output inline. The post-fix merge gets the first merge's contract and the same kind of prepared brief. Write `<plan-dir>/evidence/post-fix-readers.tsv` with one row in `pr-review-readers.tsv`'s shape — role `post-fix-red-team`, success or failure, raw artifact path — and `<plan-dir>/evidence/post-fix-diff-files.txt` with `git diff --name-status <anchor> <candidate commit>`, the anchor being `Settled candidate` when set and `Diff base` otherwise. Build the brief on the recomputed post-fix fingerprint:

```bash
"{{OUTPUT_ROOT}}/bin/pln-build-review-brief" --mode pr-merge \
  --contract "{{SKILL_DIR}}/src/workers/pr-review-merge.md" \
  --root "<repository-root>" --candidate "<post-fix-candidate-sha256>" \
  --commands "<plan-dir>/evidence/review.commands" \
  --environment "<plan-dir>/evidence/review.environment" \
  --plan "<plan-dir>/PLAN.md" --ledger "<plan-dir>/REVIEW.md" \
  --diff-map "<plan-dir>/evidence/post-fix-diff-files.txt" \
  --reader-metadata "<plan-dir>/evidence/post-fix-readers.tsv" \
  --artifact post-fix-red-team "<plan-dir>/evidence/post-fix-red-team.json" \
  --skill-root "$(dirname "{{SKILL_DIR}}")" \
  --out "<plan-dir>/evidence/post-fix-merge.brief"
```

Omit `--plan` only for a standalone run, and stop on a manifest over the helper's count bound, as for the first merge. Spawn one fresh `judgment`-profile merge worker under `{{SKILL_DIR}}/src/workers/pr-review-merge.md` on that brief, with `<plan-dir>/evidence/post-fix-merge.md`, `<plan-dir>/evidence/REVIEW.g<next-generation>.next.md`, `<plan-dir>/results/post-fix-merge.txt`, routing attribution, a 4096-byte budget, the current Run identity and the next Ledger generation. Its assignment also carries the duties of this round that the contract does not: the exact range the red team was scoped to, or that it read the whole candidate; judge each fix from the fix worker's regression-first evidence and rerun suites only as the verifier paragraph above allows; rerun the structural checks above for each structural finding; and return `reader_commit` — the candidate commit the red team or verifier read when the merge counted that reader's artifact successful, or `none`. Validate the envelope, then publish its candidate through the phase's ledger boundary. One malformed retry, then fail closed. Once it is published, file each title in the merge envelope's `pre_existing` field once with `{{OUTPUT_ROOT}}/bin/pln-todo add`, `--source` naming this review and the finding; a defect the base already had is filed and named, never repaired on this branch.

- If the red team confirms and finds nothing blocking: record its non-blocking notes in `REVIEW.md`. Only the ones that clear the follow-up bar (Style's "Ending a message") reach the closing message's bullet list and the PR body; the rest stay internal.
- If it surfaces a verified actionable finding: add or reopen it in `REVIEW.md` and apply the progress protocol below. Do not ask whether to begin another repair round.

**The settled candidate — what a later round is allowed to be about.** `Settled candidate` in `REVIEW.md` is the commit the last successful post-fix reader read. It is empty until the first post-fix reader, which runs once every finding from the rostered review is closed, skipped or filed, and reads the whole candidate. A value that does not resolve with `git rev-parse --verify "<value>^{commit}"` — the fingerprint an older release recorded here — counts as empty, so that round reads the whole candidate. Record it from the post-fix merge result, never at dispatch: when the published envelope's `reader_commit` names a commit, that commit becomes `Settled candidate`. A failed or uncounted reader leaves `Settled candidate` where it was, so bytes no reader read successfully are read in the next round. Every post-fix reader spawned while it is set gets a narrowed brief, and the narrowing is the whole brief rather than an aside in it: **review exactly `git diff <Settled candidate> <candidate commit>`, and nothing else**, with `bin/pln-assurance diff-fingerprint --root <repository-root> --base <Settled candidate>` as that range's identity in the brief and the ledger. What a regression hunt is for is what the latest repairs broke; it is not a fresh opportunity to reread bytes an earlier reader already read. A defect outside that range is out of scope for this run and files as a follow-up — not because it is unreal, but because this branch already bought one reading of those bytes and a second one is a different purchase. The exception is narrow and stays open forever: code outside the range — base code or an earlier round's repair code — that the range now lets the reproduction's input reach is a repair consequence, in scope, and repaired.

This is a scope rule, not a round cap, and the difference is the thing 1.x deliberately protected. Nothing counts rounds and nothing stops on a count. A verified regression a repair introduced is repaired however many rounds that takes, and the same-defect stuck threshold is still the only thing that ends the loop. What changes is the surface each later round can report on: it is only what the previous round's repairs changed, so every repair byte gets one successful reading and no round rereads what an earlier one read. That bounds each round by its own repairs rather than by everything changed since review, and it replaces waiting for a fresh reader to find nothing on a whole candidate — a fixed point that does not arrive, because the candidate changes under every reader that does find something. It does not by itself end a loop whose every repair introduces a new defect; smaller repairs do that. Observed: one release's plan drew four full R3 rounds at four readers each; the third was a full re-review that reopened items the user had never edited and the previous round had already cleared, and superseded its own earlier findings for all four items.

**Repair progress, not a global round cap.** Adoption of `PR after implementation`, or direct invocation of `{{PLN_PR_CMD}}`, is standing authority to repair every verified, unambiguous, in-scope finding — a `pre-existing` one is not in scope, and carries no repair key — until assurance is clean and the PR is green. A new repair round is already-authorized repair work, not a new permission boundary. Global round count never blocks it.

The merge worker assigns each verified actionable finding a stable **repair key**. Behavioral keys use the affected boundary and runnable reproduction or named failing test. Structural keys use `bin/pln-assurance repair-key --kind structural` with the responsibility/invariant, established owner, and repeatable reference check or reproduction. Never key a defect by round number, finding title, or `file:line` alone, and never rewrite an existing ledger key. Preserve these fields in `REVIEW.md`: repair key, failed repair attempts, last repair candidate, and last repair outcome.

For each open finding, run `bin/pln-assurance repair-action --disposition <value> --failed-attempts <n>`:

- Use `new` with zero attempts for a repair key not previously acted on. A different verified reproduction is a new finding, even when it appears in a later assurance round.
- Use `persisted` after an attempted fix leaves the same behavioral reproduction failing; increment its failed-attempt count against the candidate just tested. Fewer than three consecutive failed repair attempts returns to Step 4 with a fresh fix worker. A successful narrow reproduction resets the defect's consecutive-failure count; a later different failure gets its own key.
- Use `needs-decision`, `out-of-scope`, or `destructive` only for a genuine user-owned boundary, which a `reached_by: test-only` finding is not, and `worker-blocked` only when the repair worker returned a durable blocker rather than an incomplete or failed result.

On `ACTION=repair`, rebuild the affected clusters from the ledger, run Step 4 with fresh workers, checkpoint the candidate, and repeat the assurance appropriate to the risk. On `ACTION=block`, persist `Phase: blocker`, the reason, exact candidate, and partial-state pointers before asking the one question the blocker actually requires. For `same-defect-stuck`, name the three failed candidates and why the identical reproduction survived. Do not run the full project gauntlet during these cycles; Step 7 runs it once after assurance is clean.
