# /pln-pr phase: fix

<!-- pln:include active-turn-lifecycle -->

Read this file in full before the first fix decision or dispatch. Rebuild open clusters from `REVIEW.md`, not memory. A change the user asks for during this phase becomes a durable cluster with its own lease and checkpoint. Continue the idle fix worker for a correction within the same owner, lease and accepted premise; otherwise dispatch fresh context. The coordinator briefs, validates, commits and integrates; it does not edit product files. The fix-worker brief is inline below. Post-fix assurance uses `{{SKILL_DIR}}/src/workers/pr-review-merge.md` in its post-fix verifier mode, and a separate adjudicator uses that same contract when Step 5 requires it. Keep the cursor here while fixes and their narrow verification/checkpoints complete.

Every coordinator ledger update in this phase—decisions, checkpoints, integration status, post-fix merge, repair attempts, settled candidate, blocker cursor, and ship cursor—is a complete staged candidate published through `{{OUTPUT_ROOT}}/bin/pln-publish-review` with the current digest/generation. A post-fix merge/verifier writes only its assigned evidence, result, staged candidate and, for an adjudicator, node paths. Never let a worker or direct edit touch canonical `REVIEW.md`; stale publication means reread and reconcile.

Before asking a decision or handing off a blocked cluster, write it and all partial-state pointers durably, then set `Phase: blocker` and load that phase. Once every finding is durably `fixed`, `skipped`, `deferred`, `accepted`, `held`, `pre-existing` or `out-of-range` and the post-fix result is recorded, set `Phase: ship-watch` and load that phase before versioning, the final gauntlet, push, PR, or CI work.

### Step 4. Fix pass — clustered fix subagents

Classify each acted-on finding as **auto-fix** (mechanical, unambiguous — a null check, a missing timeout, a spec for uncovered behavior) or **needs-a-decision** (a judgment call — a design change, a tradeoff, anything where the fix isn't obvious or is destructive).

A structural consolidation uses the same routes. The single behavior-preservation owner is `{{SKILL_DIR}}/src/workers/behavior-preservation.md`; every fix worker handling a removal, replacement, or consolidation reads and applies it before editing. Before classifying or dispatching automatic work, validate the finding's complete `Safety disposition` from `REVIEW.md` against that owner. A missing or malformed record is `retain`, as is any missing, failed, unknown, empty, incomparable, or contradicted conjunct. Only a complete `admit` record with every conjunct `pass` may proceed to automatic work, and public, compatibility, persisted/stateful, consequential, or destructive work remains destructive/needs-a-decision even when its behavioral proof is complete. Structural clues cannot override the disposition.

Before editing, the worker validates the admitted baseline record and reruns the same admitted behavior suite on the actual pre-change source; afterward it reruns that suite under equivalent inputs and environment. Existing behavior-oriented tests are primary; implementation-detail or post-only tests may supplement, never replace, that common boundary. Automatic deletion still requires private reachability, bounded consumer closure, and repository-native discovery, but those facts do not replace behavior proof, and evidence that falls short of it retains the surface or becomes destructive/needs-a-decision on the same terms as above. The full repository gauntlet remains the final regression floor in Step 7. No similarity score, raw-growth threshold, deletion target, or cleanup quota can authorize a simplifying mutation.

**A finding the ledger records as `reached_by: test-only` is never one of these questions**, and never a blocker, whatever surface its proposed fix would touch. Repair it automatically where the ordinary rules already allow that, and otherwise retain it and file the follow-up — except a race finding on the branch's own code, which is held for the user rather than filed when it is not fixed, under the merge contract's race rule. The decision routes above exist for defects the shipped system can reach; spending one on a state only the test suite constructs buys a design the user did not ask for, aimed at a failure that cannot occur.

**Nothing reaches this phase that is not work.** A finding whose named consequence did not survive the merge worker's check against the source was dropped there, by that worker, and no trace of it arrives here — the fix phase has no preference queue to skip, because the decision was made once by the only reader in a position to make it. Do not reconstruct one. If you find yourself reasoning that a finding is minor but the repair looks cheap, the finding is a defect and the repair is cheap; a cheap repair is not a reason to build something and never was.

For needs-a-decision findings, select and record the repair you would build if no reply arrives, then enter the blocker phase for its two-notice window. Surface them to the user **one at a time**, as prose, in the option-message shape, with notifications before each question. **The question carries the finding's `smaller_fix` beside its proposed fix** — which smaller repair was passed over and why it lost, or that the reader found none — because a question that presents one design as the only way to close a defect asks the user to ratify the design rather than decide the tradeoff, and the reader already did the looking. Name the selected fallback plainly. A `none found` the finding's own citations contradict is worth saying so about in the same message. Record each answer or the elapsed-window fallback in `REVIEW.md` against its finding. A skipped finding is marked `skipped`; it becomes a follow-up in the closing message's bullet list only if it clears the follow-up bar (Style's "Ending a message") — someone will actually need to act on it or decide about it later. A skip that was really "not worth doing" gets no follow-up entry.

**A finding goes to the blocker phase only when there is a fork.** Before it does, check the selected repair against every other one. If each other repair leaves the finding's `breaks_if_shipped` consequence in place, contradicts a quoted owner constraint or a `Decision (user, …)` entry in `PLAN.md` or `REVIEW.md`, or would revert commits that later commits build on, the selected repair is the only real one: build it as an ordinary repair and record the repair passed over and why in `REVIEW.md`. This covers needs-a-decision findings whose repair has no consequential surface; a repair that adds an external effect or a public export still takes the consequential-repair route below, and a destructive one still takes its own gate. A question the user would answer "your pick" was never a question, and an unattended run that stops on it idles until the user is back.

**A finding marked `second_answer: yes` is a rebuild-or-adapt question, and the smaller-fix default does not apply to it.** The branch answers a question the repository already answers, and the smallest repair is usually to make the new answer imitate the old one, which keeps both. It is needs-a-decision, asked through the blocker phase like any other, with two options, unless rebuild is not a real one: when the commits it would revert are ones later commits build on (`PLAN.md`'s dependency edges; standalone, later commits in the range that touch the same files), or when the rebuild answer contradicts a quoted owner constraint or a `Decision (user, …)` entry, adapt is the only repair. Build it without asking and record rebuild as the repair passed over, with the reason. Otherwise there are two options, each described by the code that would survive it — how many places answer the fact afterwards, and which paths and compatibility shims remain — never by lines changed or work already done:

- **Adapt** — repair the branch in place so the fact is read through one owner.
- **Rebuild** — undo the work that was built on the second answer and do it again on the one owner. The question names the commits it would revert: with a `PLAN.md`, the commits its affected items record; standalone, `git log <diff base>..HEAD -- <cited files>`.

When both are real, neither is preferred in advance; which one leaves the better code is the user's call. A timeout selects adapt, never rebuild. On rebuild, record the answer verbatim in `Owner constraints`, revert those commits with `git revert --no-edit` (new commits; history is never rewritten), and record the revert commits in `REVIEW.md`. A revert that does not apply cleanly stops at the blocker phase, naming the conflict. Then dispatch the work again as a cluster. With a `PLAN.md`, each affected item is redone by a fresh worker under `{{SKILL_DIR}}/src/workers/item-implementation.md`, reading its own item section, with `commit owner: coordinator`. Standalone, one fix worker redoes what the reverted commits did, with their messages as its spec. The post-fix review then reads the rebuilt work.

**Restoring adopted baseline behavior does not repeat its approval.** The ledger must carry the independent merge's restoration basis: the quoted adopted behavior, base source and non-test caller, runnable reproduction with the same inputs and persisted/external/public effects, retained owner, and comparison showing the selected repair restores that behavior without adding policy, effects, scope or destruction. Compare to the accepted base-reachable behavior, not the broken candidate. Copy that basis into the fix brief; the worker checks its exact candidate and proposed delta against it before editing. Missing, stale, ambiguous or contradicted evidence takes the ordinary gate. An owner conflict, a new business policy or consequential effect, destructive expansion, or a live action still needs its actual authorization; a restoration record authorizes code repair, never the live action. It does not reclassify a proposed structural removal, replacement or consolidation under `behavior-preservation.md`; its public/stateful/destructive boundaries still apply.

**Ask before a consequential repair outside that adopted restoration; an unanswered question does not idle the run overnight.** A production-reachable repair that would add a persisted-state write or transition, a call with an external effect, or a public export returns `BLOCKED:` before any edit or new spec, whatever its `branch_purpose`, unless the independently evidenced restoration above covers the exact selected repair. The blocker phase asks and notifies, reminds after five minutes without an answer, then after five more minutes records the user's standing fallback authorization and resumes the selected repair. A reply at any point before resumption wins, and any reply ends the timer for that question: it then waits for the user's answer. The question names the proposed and smaller repairs and what each adds; the fallback is the repair selected by the brief's smaller-fix rule, never a newly invented third design. State the branch itself introduces and nothing outside it has acted on is not one of these surfaces (the worker brief names the test), so repairing it never reaches the window. The resumed brief quotes the recorded answer or timeout authorization, so the worker does not block on the same gate twice. An explicit owner constraint is never lifted by a timer.

A finding whose every available repair the owner's recorded constraints rule out is `deferred` and filed once with `{{OUTPUT_ROOT}}/bin/pln-todo add --status proposed --do <its repair> --done-when <the finding's reproduction passing>`; record the quoted constraint and keep its repair key. If that finding is the branch's quoted purpose or a CI fix, enter the ordinary blocker instead: the owner must lift the constraint, and silence cannot do it. A `reached_by: test-only` finding whose only repair adds one of the three consequential surfaces is also deferred; it does not spend a user decision. A race finding is the exception: left unbuilt for that reason, it is held, not deferred or filed. The worker leaves these unbuilt, finishes the rest of its cluster, and names the reason. At the checkpoint publish `deferred`, and publish a race finding the worker named held as `held`, its title added to `Draft hold`; a cluster with no edits checkpoints with `{{SKILL_DIR}}/bin/pln-scheduler checkpoint --commit none`. A later merge keeps the status and does not refile it. A reachable finding whose standing timeout authorization the host refused to act on is also deferred, by the blocker phase's rule; a reachable finding is not otherwise deferred merely because its fix is consequential. These are the only deferral routes here.

**No worker schedules a repair round.** The merge worker that declared the clusters also wrote `<plan-dir>/fix-nodes.tsv` under `{{SKILL_DIR}}/src/workers/execution-schedule.md`'s rules, from `<plan-dir>/fix-dirty-start.tsv`, the snapshot taken before that merge was dispatched: dependencies, overlapping/ancestor leases, generators, lockfiles, tests, configuration, migrations, and shared effects add edges, and unknown means serial. Observed before this: every multi-cluster round spawned its own scheduling worker, 5–7 minutes each, and every one returned a linear order. Use the node file as written only when the clusters about to be dispatched are exactly the ones it declares. Otherwise edit it mechanically before building: remove the rows of clusters not being dispatched — skipped, or answered away — and their numbers from every `DEPS`; then append each new, re-dispatched or re-scoped cluster (a user-requested change, a `persisted` retry, an `ACTION=repair` rebuild, a resumed `BLOCKED:` cluster) as a row with `DEPS` naming every earlier row, `COHORT=-`, `CONTEXT=fresh`, `DIRTY_STATE=unknown`, and as its lease the cluster's declared file set — the files of both its `fix` and its `smaller_fix`. Execution is linear, so appending serially is always a valid order; when no merge declared this round's clusters — a change the user asked for between rounds — retake the snapshot now and the appended rows are the whole file, never an earlier round's rows. Then run `{{SKILL_DIR}}/bin/pln-scheduler build --root <plan-dir> --nodes <plan-dir>/fix-nodes.tsv --manifest <plan-dir>/fix-manifest.tsv --source-root <repository-root> --source-head <HEAD> --dirty-snapshot <plan-dir>/fix-dirty-start.tsv --repo-mode git|non-git`. Independent clusters start fresh; clusters the schedule had to order may share a worker under the cohort boundaries. Execution is linear either way — one cluster at a time, in the working tree the run was launched in. `REVIEW.md`, the manifest, git checkpoints, and integration are coordinator-only. Auto mode never applies to `{{PLN_PR_CMD}}`.

**A constraint the owner added since the last merge re-judges the open findings before the next dispatch.** Before dispatching a cluster, count the entries in `REVIEW.md`'s `Owner constraints` (`none stated` is zero). When there are more than the ledger header's `Constraints judged` (absent reads zero) and any finding is `open`, dispatch nothing yet. Build a brief the way the merge that published those findings built its own — the same reader metadata, artifacts and diff map — on the current tree's recomputed candidate fingerprint, to `<plan-dir>/evidence/constraint-merge.brief`, and spawn one fresh `judgment`-profile merge worker under `{{SKILL_DIR}}/src/workers/pr-review-merge.md` on it, with `<plan-dir>/evidence/constraint-merge.md`, `<plan-dir>/evidence/REVIEW.g<next-generation>.next.md`, `<plan-dir>/results/constraint-merge.txt`, routing attribution, a 4096-byte budget, the current Run identity, the next Ledger generation, and an assignment naming it a constraint re-judge. Validate and publish its candidate with the review phase's checks, the owner-constraint checks included; one malformed retry, then fail closed. Its clusters and leases are the ones already scheduled; dispatch them with briefs copied from the republished ledger. A cluster that was already running when the constraint arrived finished on its own brief, and its repair is read by the next post-fix round like any other.

### Step 5. Post-fix assurance — the second pass

**The review runs once; the second pass checks the fixes and looks for nothing new.** Every fix creates a new candidate; recompute its exact fingerprint before assurance. A round in which no cluster changed the tree — every finding deferred or held — created none: it runs no post-fix reader and leaves `Settled candidate` unchanged. One fresh post-fix verifier reads the fixes and checks that each did what it said; no red-team pass follows the fixes, and the four-reader cap is the review's alone. A trivial fix still gets that fresh verifier — the coordinator validated the fix and may not also certify that no deeper review was needed, which is the whole reason that reader is fresh.

**That verifier judges; it does not rebuild what the fix already proved.** Use the fix worker's validated regression-first evidence — the actual pre-change failure and exact post-change command/count — only when its source/command/environment seal matches the current candidate. The verifier judges sufficiency and residual risk from that evidence and the relevant source. It reruns a suite only where the evidence is absent, incomparable, or produced under a different fingerprint, and names which applied. Independence is in the source judgment, not repeating a passing command.

Every post-fix path must rerun the structural reference check and consumer map (including direct and indirect consumers) for each structural finding and compare the recorded before/after owners, paths, and knobs. For a removal, replacement, or consolidation, it also rechecks repository-native discovery, bounded closure, and the post-change result from the same admitted behavior suite against its actual pre-change outcome under `{{SKILL_DIR}}/src/workers/behavior-preservation.md`; deletion additionally rechecks private reachability. Missing, changed, flaky, or incomparable proof reopens the same structural repair key and fails closed; do not treat passing post-change or implementation-detail tests alone as structural assurance. Step 7 still runs the full repository gauntlet once after assurance is clean.

**One independent post-fix verifier judges the repairs and prepares a clean ledger.** Use `{{SKILL_DIR}}/src/workers/pr-review-merge.md` in `post-fix verifier` mode. It reads the exact candidate/range, verifies every attempted repair key and outcome from the regression-first evidence, checks direct and indirect consumers and structural/behavior proof where relevant, and compares owner constraints and required reader coverage. An empty findings array alone cannot certify a repair. The initial multiple-reader merge and its R3 staffing stay unchanged.

Before dispatch, write `<plan-dir>/evidence/post-fix-diff-files.txt` with `git diff --name-status <anchor> <candidate commit>` (`Settled candidate` when set, otherwise `Diff base`), and `<plan-dir>/evidence/post-fix-readers.tsv` with the assigned role, `pending`, and `<plan-dir>/evidence/post-fix-red-team.json`. This pending row counts as no coverage. Retake `<plan-dir>/fix-dirty-start.tsv` with `bin/pln-scheduler snapshot`. Build a prepared brief on the recomputed fingerprint, using the helper's existing `pr-merge` inventory boundary:

```bash
"{{OUTPUT_ROOT}}/bin/pln-build-review-brief" --mode pr-merge \
  --contract "{{SKILL_DIR}}/src/workers/pr-review-merge.md" \
  --root "<repository-root>" --candidate "<post-fix-candidate-sha256>" \
  --commands "<plan-dir>/evidence/review.commands" \
  --environment "<plan-dir>/evidence/review.environment" \
  --plan "<plan-dir>/PLAN.md" --ledger "<plan-dir>/REVIEW.md" \
  --diff-map "<plan-dir>/evidence/post-fix-diff-files.txt" \
  --reader-metadata "<plan-dir>/evidence/post-fix-readers.tsv" \
  --artifact repair-evidence "<validated-fix-result-path>" \
  --skill-root "$(dirname "{{SKILL_DIR}}")" \
  --evidence-root "<Plan root>" --evidence-root "<Worker artifacts>" \
  --out "<plan-dir>/evidence/post-fix-verifier.brief"
```

Repeat `--artifact <unique-role> <path>` for every assigned repair result and each evidence/status/log file it relies on. Omit `--plan` only for a standalone run; on a manifest over the helper's count bound, narrow the skill roots as the review phase says. Spawn one fresh `judgment`-profile post-fix verifier under `{{SKILL_DIR}}/src/workers/pr-review-merge.md` on that brief, assigning `<plan-dir>/evidence/post-fix-assurance.md`, `<plan-dir>/evidence/post-fix-red-team.json`, `<plan-dir>/evidence/REVIEW.g<next-generation>.next.md`, `<plan-dir>/results/post-fix-verifier.txt`, routing attribution, a 4096-byte budget, the current Run identity and the next Ledger generation. Its assignment also carries the exact range or whole-candidate scope, known repair keys, and the source-state check against the candidate commit. No other reader runs beside or before it.

Its reading brief says: "Read the exact post-fix candidate. Check that each listed fix did what it said — that it closes its finding's reproduction and restores the behavior the finding promised — and look for nothing else. Review exactly `git diff <Settled candidate> <candidate commit>`; where the assignment names no `Settled candidate`, the whole candidate. A fix fails when `git diff --name-status <Settled candidate> <candidate commit>` shows it modifying, deleting or renaming a test file that exists at `Settled candidate`, unless its finding cites that test. Report anything else you happen to notice as a finding; it is not yours to admit. Write the complete bare JSON `{findings: [...]}` object with exact citations and runnable reproduction/test evidence; label unsupported suspicions unverified. Each finding carries severity, evidence_state, file/line, lens, summary, motivating_code, reproduction, fix, smaller_fix and the reachability/base/consequence fields below; structural evidence is optional but must be complete when present. Give each finding a `reached_by` and `breaks_if_shipped`. Give each finding an `on_base` with both the base source and non-test caller reaching the same failure with the same input, or `branch`, on the first merge's terms. Judge each known fix from its matching regression-first evidence; rerun only missing, incomparable or stale suites. Apply the structural checks above. Return only the assigned `RESULT_FILE` pointer."

**A clean reading replaces the unconditional second merger.** The verifier writes its raw findings and detailed repair-sufficiency notes file-first, then prepares the complete staged ledger only when all required reading and repair proof succeeded and it found no new or reopened repair work, conflicting readers, unresolved owner/scope constraints, or unverifiable coverage/evidence. It preserves known keys, decisions, repair outcomes and owner constraints; no new claim is admitted or scheduled by its discoverer. Its bounded envelope reports `post-fix: clean`, the counted `reader_commit`, and staged candidate path/digest. It writes no fix-node file. The coordinator validates the envelope, exact candidate/range, required reader attribution and staged ledger before publication; it never infers clean from an empty array.

**New findings or ambiguity require a separate adjudicator.** The verifier returns `post-fix: adjudication-required`, raw artifact/evidence pointers and no publishable ledger or node file when it discovers a new finding, reopens a repair, sees conflicting readers, or cannot verify required proof/coverage or constraints. Preserve failed artifacts, but they count as no successful coverage. Never open that reviewer output inline. Record its actual success/failure in `post-fix-readers.tsv`, and build `<plan-dir>/evidence/post-fix-merge.brief` with the command above, replacing the repair artifact slot with `--artifact post-fix-red-team "<plan-dir>/evidence/post-fix-red-team.json"` and also inventorying the repair evidence. Spawn one separate fresh `judgment`-profile adjudicator on the first merge's contract, with `<plan-dir>/evidence/post-fix-merge.md`, the staged ledger path, `<plan-dir>/results/post-fix-merge.txt`, the dirty snapshot and `<plan-dir>/fix-nodes.tsv`. It independently confirms each claim's reproduction, base behavior, consequence, consumers and owner constraints. A reopened known repair key goes back to repair, and it prepares that key's node. A new claim is never admitted: the adjudicator records a serious one `held` and drops the rest, under the merge contract's "After the review, nothing new is repaired". It judges known repairs from the same sealed evidence without rebuilding passing commands. A failed reader or missing required proof cannot become a clean review merely because adjudication found no findings.

For either publishable result, require the staged `Phase` cursor to equal the canonical cursor at dispatch; a review outcome belongs in `Post-fix`, never in `Phase`. Only the coordinator advances the phase after validated publication. Check every `accepted` finding as the first merge does: its quoted decision entry begins `**Decision (user`, or `**Decision (agent).**` for a prevention the interview took, and occurs byte-for-byte in that `PLAN.md`, and its basis field is present. **Reject a candidate that carries a repair key the ledger it was dispatched on does not**: after the review, a key enters only through a CI fix cluster, a final-gauntlet repair or a change the user asks for, each written to the ledger before its dispatch. That is one malformed result like any other. Check the owner's constraints: the candidate's `Owner constraints` field is byte-identical to the canonical field the merge was dispatched on, its `Constraints judged` is that field's entry count, and every actionable finding's `owner_constraint_fix` and `owner_constraint_smaller_fix` is `none`, an exact entry less its leading `- `, or an applicable exact `**Decision (user` entry. Publish only through `pln-publish-review` with the dispatch digest/generation; stale publication requires reconciliation. One malformed retry, through a separate fresh adjudicator, then fail closed. An `accepted` finding is never filed. File each title in the merge envelope's `pre_existing` field once with `{{OUTPUT_ROOT}}/bin/pln-todo add`, `--source` naming this review and finding, `--do`/`--done-when` its repair and reproduction; a post-fix round names none, since it drops what it finds on the base. Add each title in its `held` field to `Draft hold`. A reopened repair applies the progress protocol below without asking whether to begin another round.

**The second pass rebinds the reviewed subject.** When a published second pass leaves no finding `open`, record `bin/pln-assurance diff-fingerprint --root . --base "origin/<base>"`'s `DIFF_BASE` and `REVIEW_DIFF_SHA256` as the ledger's diff base and reviewed-diff SHA-256: the fixes have now been read, so ship-watch's reconciliation catches only bytes that changed after this pass, and does not send a fixed branch back to a second review.

**The settled candidate — the commit the review read.** `Settled candidate` in `REVIEW.md` is the candidate commit the review's readers read. The review phase records it when it publishes the review, and nothing moves it after. A value that does not resolve with `git rev-parse --verify "<value>^{commit}"` — the fingerprint an older release recorded here — counts as empty, and so does an empty one in a ledger an older release wrote: that round reads the whole candidate. Every post-fix reader gets a narrowed brief, and the narrowing is the whole brief rather than an aside in it: **review exactly `git diff <Settled candidate> <candidate commit>`, and nothing else**, with `bin/pln-assurance diff-fingerprint --root <repository-root> --base <Settled candidate>` as that range's identity in the brief and the ledger. That range is the fixes, and the second pass is about whether each one did what it said. The review already read everything else, once.

This is a scope rule, not a round cap, and the difference is the thing 1.x deliberately protected. Nothing counts rounds and nothing stops on a count. A fix that does not do what it said — its reproduction still fails, or it changed a test the review read — is redone, and the same-defect stuck threshold is still the only thing that ends that. What a later round cannot do is find new work: a new finding is held for the user when it is serious and dropped otherwise, never repaired. Observed: across two months of runs over an hour long, the median spent 39% of its agent time in `{{PLN_PR_CMD}}` against 18% implementing, mostly in post-fix rounds repairing the previous round's repairs; one release's plan drew four full R3 rounds at four readers each, the third a full re-review that reopened items the previous round had already cleared.

**Repair progress, not a global round cap.** Adoption of `PR after implementation`, or direct invocation of `{{PLN_PR_CMD}}`, is standing authority to repair every verified, unambiguous, in-scope finding the review admitted, and every key a CI fix cluster, a final-gauntlet repair or a change the user asks for adds — a `pre-existing` one is not in scope, and carries no repair key, and a `deferred` one is not repaired on this branch, its key kept only so a later merge can match it, and an `accepted` one is the user's decision and carries no repair key, and a `held` one waits for the user's answer — until each fix is verified and the PR is green. A new repair round is already-authorized repair work, not a new permission boundary. Global round count never blocks it.

The merge worker assigns each verified actionable finding a stable **repair key**. Behavioral keys use the affected boundary and runnable reproduction or named failing test. Structural keys use `bin/pln-assurance repair-key --kind structural` with the responsibility/invariant, established owner, and repeatable reference check or reproduction. Never key a defect by round number, finding title, or `file:line` alone, and never rewrite an existing ledger key. Preserve these fields in `REVIEW.md`: repair key, failed repair attempts, last repair candidate, and last repair outcome.

For each open finding, run `bin/pln-assurance repair-action --disposition <value> --failed-attempts <n>`:

- Use `new` with zero attempts for a repair key not previously acted on: one the review admitted, or one a CI fix cluster, a final-gauntlet repair or a change the user asked for added. A different verified reproduction a later round notices is not a new finding to repair; the adjudicator holds it or drops it.
- Use `persisted` after an attempted fix leaves the same behavioral reproduction failing; increment its failed-attempt count against the candidate just tested. Fewer than three consecutive failed repair attempts returns to Step 4 with a fresh fix worker. A successful narrow reproduction resets the defect's consecutive-failure count; a later different failure is a new finding, which that round holds or drops.
- Use `needs-decision`, `out-of-scope`, or `destructive` only for a genuine user-owned boundary, which a `reached_by: test-only` finding is not, and `worker-blocked` only when the repair worker returned a durable blocker rather than an incomplete or failed result.

On `ACTION=repair`, rebuild the affected clusters from the ledger, run Step 4 with fresh workers, checkpoint the candidate, and run Step 5's second pass on it. On `ACTION=block`, persist `Phase: blocker`, the reason, exact candidate, and partial-state pointers before asking the one question the blocker actually requires. For `same-defect-stuck`, name the three failed candidates and why the identical reproduction survived. Do not run the full project gauntlet during these cycles; Step 7 runs it once after assurance is clean.
