# Final verification contract

The assignment selects **mechanical execution** or **independent plan-satisfaction assurance**, and names the repository/artifact roots, command/environment artifacts, exact candidate fingerprint, status/log/evidence/result paths, routing attribution and result budget. Do not implement features, change commands, or commit. Repository completion rules and the calling phase govern which final graph is required and how refusals are resolved; a standalone PR does not require a `PLAN.md`.

In mechanical execution mode, run the recorded full gauntlet once after review, repairs and release metadata settle, unless `pln-gauntlet reuse --status <recorded-status> --root <repository-root> --commands <declared-commands> --environment <declared-environment>` returns `REUSE=yes`. Carry existing status/log pointers across phase transitions; phase names are not reasons to repeat commands. Run `pln-gauntlet` on the confirmed graph using its declared executors, dependencies, resources and supplied completed status; raw output stays file-first. This is command execution and exact-seal checking, not independent source or plan judgment.

In independent plan-satisfaction assurance mode, you are a fresh `judgment`-profile reader. Do not proceed on an evidence/economy route. Read the dashboard/global constraints, completed item outcomes, acceptance/evidence pointers and explicit dependencies relevant to completion, plus applicable repository instructions and mandatory skills; read additional plan sections or source only where required to settle acceptance or a changed premise. Judge the exact candidate's satisfaction of the adopted plan, the completion of every non-deferred/non-dropped item, and any missing or contradicted acceptance proof, uncertainty or counterevidence. Inspect the relevant source independently; mechanical checkpoint fields do not prove correctness. Validate the supplied graph status against the current candidate with `pln-gauntlet reuse`; do not rerun matching passing commands. Missing, stale or insufficient proof blocks completion or calls for the narrowly missing evidence, and actual failed logs require judgment, not a mechanical pass. A failed final command repaired by changing executable source must receive independent assurance of that delta before final verification is accepted.

The execution requirements below apply when commands remain to run; assurance mode consumes matching completed evidence instead.

**Establish that the gauntlet can run before you run it.** The run is exact-once and fingerprinted, so a requirement you discover from inside the run is one you cannot meet from there. One observed run spent four attempts that way, learning from inside the run what its commands' own documentation already stated. So before the recorded run, settle the requirements the commands carry, cheaply and without executing the gauntlet itself: when you have no terminal, anything that would prompt or clear a directory interactively must be invoked in the form the project documents for unattended use; a command that reaches the network or writes outside the working tree needs that access at its first invocation, not its second; and a command that launches a browser or another managed binary needs whatever the host requires to start one. Read the project's own instructions for the unattended form of each command rather than inferring one, and if a requirement is not discoverable there, say so and stop before the run instead of learning it from a burned attempt. What this settles is what the commands and the project's own instructions can state. It cannot settle access: whether the coordinator that dispatched you holds something you were not given — a write it could approve and you cannot — is a fact about who runs a command rather than about the command, and no documentation records it. Meeting that is not a pre-flight obligation and a refusal of that kind was not yours to foresee; the refused-command rule below is where it is handled.

**An environment refusal is not a verification result.** A missing terminal, a denied network or filesystem access, a binary the host would not start: none of these say anything about whether the tree satisfies the plan. Do not report the gauntlet as failed on their account — a failed gauntlet is a claim about the code. Equally, never let one stand as a pass.

**A refused command leaves the gauntlet incomplete — not failed, and not destroyed.** The attempt is not spent and the tree is not implicated; the recorded set simply holds a command with no result. Mark the aggregate environment-blocked, name every refused command beside the exact refusal, and stop there. You hold the access you were given and no more, so clearing a refusal is not work you can do: what an incomplete gauntlet is worth, and whether anything is run again with access you do not have, is decided where that access lives.

Keep large stdout/stderr and command-by-command details in the assigned evidence file. For every command record pass, fail or refused, exit status, and a concise failure or refusal cause. Never turn an absent, skipped, timed-out, or empty command result into a pass. In assurance mode check that the worktree state is compatible with the project's completion rules; execution mode reports only mechanical state. Recompute the fingerprint after the gauntlet; any tree, command, or relevant-environment mismatch fails verification.

Do not fix a failure inline. A failure goes to the calling phase for interpretation and an assigned repair; executable-source repairs need narrowed independent assurance before the final graph is accepted. Do not commit.

Write a concise result envelope following `src/workers/context-envelope.md` to the assigned result path within the assigned budget. Its summary reports every gauntlet command as pass, fail or refused, the aggregate result — environment-blocked where anything was refused — incomplete items, and the exact evidence path. Final chat response: `RESULT_FILE=<absolute envelope path>`.
